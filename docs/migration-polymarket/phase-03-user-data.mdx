# Phase 3. Read-only user data

## Scope

Read paths from the frontend and SSR to `data-api.polymarket.com` (env
`DATA_URL` and `USER_PNL_URL`, which after Phase 0 share the same host). This
phase covers what fills profile pages, the portfolio screen, the leaderboard,
the activity feed, the event-page top holders, the profile hover card, and the
profile PnL chart.

Out of scope here: comments and community profile management (Phase 7, which
also handles the `COMMUNITY_URL` host whose status is established below for
context but not addressed); referrals/affiliate UI which depends on the
`/referrers` data-api endpoint (Phase 10); writing positions/orders (Phase 4);
websockets that push activity/trade updates (Phase 6).

## Findings

### Finding 1. `/positions`, `/closed-positions`, `/activity`, `/value`, `/holders`, `/trades` work as-is; mappers already match Polymarket's contract

**Claim.** Five of the six high-traffic data-api endpoints we hit return a
shape that lines up exactly with the TypeScript interfaces in
`src/lib/data-api/user.ts` and `src/lib/data-api/holders.ts`. No mapper edits
required for these.

**Evidence.**

- Live probe responses listed above. Cross-walked field-by-field against
  `DataApiPosition` (`user.ts:35-63`), `DataApiActivity` (`user.ts:11-33`),
  `DataApiHolder` / `DataApiHoldersResponse` (`holders.ts:3-17`), and the
  `usePortfolioValue` accessor at `usePortfolioValue.ts:54`.
- Sort param fallback in `usePublicPositionsQuery.ts:172-184` already retries
  without `sortBy`/`sortDirection` if Polymarket complains — defensive design
  that survives schema drift.

**Impact.** No code changes for the active paths. Confidence to move forward.

**Confidence.** High. End-to-end live probe with a real wallet that has both
active and closed positions on Polymarket.

### Finding 2. `/user-pnl` does not exist on `data-api.polymarket.com`; the profile PnL chart and the leaderboard PnL hydration are both broken

**Claim.** The PnL chart on `/profile/<slug>` (driven by `usePnlSeries` at
`PublicProfileHeroCards.tsx:71`) and the leaderboard's per-row PnL augmentation
(driven by `/api/leaderboard/timeframe-pnl/route.ts`) both call
`USER_PNL_URL/user-pnl?user_address=…&interval=…&fidelity=…`. Polymarket
returns HTTP 404 for every variant of this path I tested. The user-pnl service
does not appear to be public on `data-api.polymarket.com`.

**Evidence.**

- Live probe, this session: `GET data-api.polymarket.com/user-pnl?...`,
  `?user_address=…`, `?...&interval=1d`, all 404.
- Code: `usePnlSeries` PNL fetch at `PublicProfileHeroCards.tsx:71-95`, swallowed
  by `.catch(...)` at `:111` (sets `pnlSeries: []`).
- Code: `/api/leaderboard/timeframe-pnl/route.ts:212-220` reads
  `await fetch(`${endpoint.toString()}?${params.toString()}`)` and returns
  `null` on `!response.ok`. The leaderboard hydrator
  (`leaderboardApi.ts:189`) catches and returns an empty Map.
- Phase 0 framework asserts `USER_PNL_URL=https://data-api.polymarket.com`. So
  both consumers point at the same broken host.

**Impact.** Profile pages render with a zeroed PnL chart (the fallback path in
`PublicProfileHeroCards.tsx:475`). The leaderboard renders entries but the
"Profit/Loss" column shows nothing useful for the timeframe dimension because
`hydrateEntriesWithPortfolioPnl` returns the unchanged entries
(`leaderboardApi.ts:191-193`). Visible behavior: leaderboard works, but the
sorted-by-pnl ordering reflects only the lifetime-pnl baked into the
`/v1/leaderboard` payload, not the `timeframe`-relative pnl our UI presents.

**Confidence.** High. Direct probes; both consumers wrap the call in catches
that turn a 404 into a silent fallback, so this is the kind of defect that
ships invisibly.

**Resolution paths (decide in this phase).**

A. Drop the per-row pnl hydration entirely. Use the lifetime pnl returned by
   `/v1/leaderboard` directly. Tradeoff: the period-filtered leaderboard would
   show all-time pnl, which is a regression.

B. Replace `/user-pnl` with a path that does exist. The lifetime aggregate
   pnl is in the `/v1/leaderboard` response per row. The per-period pnl is
   embedded in the same response when `timePeriod=day|week|month` (live probe
   confirmed: each row has a `pnl` field that is period-specific). So we can
   skip the secondary `/user-pnl` call entirely.

C. Stand up our own user-pnl service. Out of scope for launch-this-week.

The recommended path is B: trust the `pnl` field on
`/v1/leaderboard?timePeriod=…` instead of recomputing from a non-existent
endpoint. That makes both `usePnlSeries` and the timeframe-pnl batcher
unnecessary for the leaderboard path. The profile PnL chart still has no
direct substitute, so it should hide rather than show a flat baseline (this
is a UX choice; flag for review).

### Finding 4. Leaderboard `apiValue` map is correct; uppercase fallback constants in `resolve*ApiValue` are wrong but rarely hit

**Claim.** The leaderboard filter mapping in
`leaderboardFilters.ts:91-101` resolves `period`, `category`, `order` to the
correct lowercase values when an option matches. Fallbacks are `'OVERALL'`,
`'DAY'`, `'PNL'` (uppercase) which Polymarket rejects (live probe).

**Evidence.**

- Code:
  ```ts
  export function resolveCategoryApiValue(value: CategoryValue) {
    return CATEGORY_OPTIONS.find(option => option.value === value)?.apiValue ?? 'OVERALL'
  }
  export function resolvePeriodApiValue(value: PeriodValue) {
    return PERIOD_OPTIONS.find(option => option.value === value)?.apiValue ?? 'DAY'
  }
  export function resolveOrderApiValue(value: OrderValue) {
    return ORDER_OPTIONS.find(option => option.value === value)?.apiValue ?? 'PNL'
  }
  ```
- `PERIOD_OPTIONS.apiValue` are `day | week | month | all` ✓.
- Live probe: `timePeriod=DAY` → `{"error":"invalid time period parameter"}`.

**Impact.** Low in practice — the fallback only fires if a `LeaderboardFilters`
value somehow got past `PERIOD_VALUES` validation (which it can't via
`leaderboardFilters.ts` URL parsing). But: `'PNL'` for orderBy is the
documented uppercase form on Polymarket and `/v1/leaderboard?orderBy=PNL`
worked in my probe — so order is uppercase. So the fallbacks are
asymmetrically wrong: `'DAY'` and `'OVERALL'` should be `'day'` and `'overall'`,
but `'PNL'` is correct.

**Confidence.** High.

**Resolution.** Trivial lowercase fix in two of three fallbacks. P3.

## Risks

1. **A1 deletes the timeframe-pnl proxy that has internal caching.** That
   route had 60s in-memory caching with concurrency limits and request
   coalescing — careful work. Removing it deletes the only caching layer for
   Polymarket's already-cached `/v1/leaderboard`. If we hit rate limits on
   Polymarket's leaderboard endpoint at scale, we lose the buffer. Mitigation:
   add a basic 30s cache header to the OG and SSR uses of `/v1/leaderboard`.
   Park as a Phase 11 cutover concern.

2. **A2 may hide a chart that *should* show data.** If we later discover a
   Polymarket endpoint that returns user pnl series, the placeholder will
   linger because nobody re-enables it. Mitigation: leave a comment with the
   discovery target ("revert when /user-pnl or equivalent ships on
   data-api.polymarket.com").

3. **A3 hides revenue surfaces from admins.** The admin affiliate page
   currently shows referral takes; in production this is real money. Hiding
   the page until Phase 10 is correct (it's broken anyway), but mark it
   prominently in the migration changelog so the team knows their affiliate
   metrics are stale until Phase 10 lands.

4. **A4 has a hidden dependency on Phase 1.** Phase 1's gamma sync currently
   doesn't persist `gamma_event_id`. Until that ships, A4 can't ship.
   Order Phase 1 A3 + Phase 3 A4 in the same PR.

5. **`/v1/leaderboard` per-row `pnl` semantics are unclear at the period
   boundary.** Live probe with `timePeriod=week` returns `pnl: 822273.47` for
   a row. Need to confirm whether that's "weekly pnl" or "lifetime pnl bounded
   to weekly volume". If it's the latter, A1's premise breaks. Resolution:
   pick three rows, fetch them at `day`, `week`, `month`, `all` and verify
   the `pnl` field changes per period. Add this to the A1 acceptance test.
