# Phase 13. Final sweep

## Why this phase exists

User pressed for 100% coverage. Four areas Phases 1-12 didn't fully nail:

1. **Comments UI**: Phase 7 confirmed gamma supplies the read shape, but didn't enumerate the field-by-field mapping into our existing `Comment` interface and the 11 components that consume it.
2. **Geoblock**: Phase 9 had a hand-rolled middleware sketch using `request.geo`. The current Vercel-canonical pattern is `geolocation()` from `@vercel/functions`, demonstrated in `vercel/examples/edge-middleware/geolocation-country-block`.
3. **Fee mechanism + builder code in EIP-712**: Phase 4 Finding 4 left the builder-code-placement question open. New evidence resolves it: builder code is part of the V2 Order struct (signed). And builder fees flow natively through Polymarket — no separate skim needed.
4. **Admin: configure builder wallet/fee from the dashboard**: Phase 10 mentioned `polymarket.com/settings?tab=builder` for fee configuration but didn't plan the mirror admin surface inside Axes.

This is the gap-closing phase. Phase 14 is launch.

### Comment write — explicit decision for launch

**Read-only at launch.** Hide all write affordances behind `process.env.NEXT_PUBLIC_COMMUNITY_WRITES_ENABLED === 'true'` (default `'false'` post-cutover). When/if Polymarket exposes a public write endpoint, we set the flag. When/if we stand up our own community service later, same.

This is more conservative than Phase 7 A2 (which gated on `COMMUNITY_URL.includes('axes.co')`); the env-var approach is cleaner because it doesn't conflate hostname with capability.

### A new helper file: `src/lib/comments/polymarket-adapter.ts`

```ts
import type { Comment } from '@/types'

interface PolymarketCommentProfile {
  name?: string
  pseudonym?: string
  displayUsernamePublic?: boolean
  bio?: string
  proxyWallet?: string
  baseAddress?: string
  profileImage?: string
  profileImageOptimized?: string
}

interface PolymarketComment {
  id: string
  body: string
  parentEntityType: 'Event' | 'Comment'
  parentEntityID: number
  userAddress: string
  createdAt: string
  updatedAt?: string
  profile: PolymarketCommentProfile
  reportCount?: number
  reactionCount?: number
}

export function adaptPolymarketComment(
  raw: PolymarketComment,
  currentUserAddress: string | null,
): Comment {
  const profile = raw.profile ?? {}
  const username = profile.displayUsernamePublic
    ? profile.name?.trim() || profile.pseudonym || raw.userAddress
    : profile.pseudonym || raw.userAddress
  const avatar = profile.profileImageOptimized || profile.profileImage || ''

  return {
    id: raw.id,
    content: raw.body,
    user_id: raw.userAddress,
    username,
    user_avatar: avatar,
    user_address: raw.userAddress,
    user_proxy_wallet_address: profile.proxyWallet ?? null,
    likes_count: raw.reactionCount ?? 0,
    replies_count: 0,                  // hydrated separately when we fetch replies
    created_at: raw.createdAt,
    is_owner: Boolean(
      currentUserAddress
      && raw.userAddress.toLowerCase() === currentUserAddress.toLowerCase()
    ),
    user_has_liked: false,             // no public per-user reaction API
    positions: [],                     // not on gamma
    recent_replies: undefined,
  }
}
```

This adapter goes in Phase 7 A1's PR and feeds every comment hook + `useHeroComments`.

## 2. Geoblock — Vercel-canonical pattern

### Verbatim from Vercel docs (this session)

> Vercel deployments automatically provide three geolocation headers:
>
> - `X-Vercel-IP-Country` — the 2-letter country code of the IP sending the request.
> - `X-Vercel-IP-Country-Region` — the ISO 3166-2 region code associated to the IP.
> - `X-Vercel-IP-City` — the city name associated to the IP.

> The `@vercel/functions` package provides a `geolocation()` helper that returns location information for an incoming request with properties including city, country, latitude, longitude, and region.

### Verbatim from `vercel/examples/edge-middleware/geolocation-country-block/middleware.ts`

```ts
import { geolocation } from '@vercel/functions'
import type { NextRequest } from 'next/server'

const BLOCKED_COUNTRY = 'AT'

export default function middleware(req: NextRequest) {
  const country = geolocation(req).country || 'US'

  if (country === BLOCKED_COUNTRY) {
    return new Response('Blocked for legal reasons', { status: 451 })
  }
  return new Response(`Greetings from ${country}, where you are not blocked.`)
}
```

### Decisions for our middleware

- **Use `geolocation()` from `@vercel/functions`** rather than `request.geo` (which still works but is deprecated in favor of the helper).
- **Default to `'US'` on missing country** so the block fails CLOSED for the most-restricted jurisdiction (matches the Vercel example's choice). But also recognize this means devs developing locally will be region-blocked unless they bypass the middleware in dev.
- **Skip middleware in development** by checking `process.env.NODE_ENV === 'development'` at the top.
- **HTTP status 451** ("Unavailable For Legal Reasons") — matches the Vercel example, semantically correct.

### Updated middleware spec for Phase 9 A1 (replaces the hand-rolled sketch)

```ts
// src/middleware.ts
import { geolocation } from '@vercel/functions'
import { NextResponse, type NextRequest } from 'next/server'
import { RESTRICTED_COUNTRIES } from '@/config/region-blocks'

export const config = {
  matcher: [
    '/((?!_next/static|_next/image|favicon.ico|robots.txt|sitemap.xml).*)',
  ],
}

export default function middleware(request: NextRequest) {
  if (process.env.NODE_ENV === 'development') {
    return NextResponse.next()
  }

  const { country } = geolocation(request)
  const resolvedCountry = country || 'US'  // fail closed

  if (RESTRICTED_COUNTRIES.has(resolvedCountry)) {
    // Read-only paths still pass; only the action surface is blocked.
    if (isReadOnlyPath(request.nextUrl.pathname)) {
      return NextResponse.next()
    }
    const url = request.nextUrl.clone()
    url.pathname = `/${request.nextUrl.locale ?? 'en'}/region-restricted`
    const response = NextResponse.rewrite(url)
    response.headers.set('x-axes-region-block', resolvedCountry)
    return response
  }

  return NextResponse.next()
}

function isReadOnlyPath(pathname: string) {
  return (
    pathname === '/'
    || pathname.startsWith('/event/')
    || pathname.startsWith('/leaderboard')
    || pathname.startsWith('/activity')
    || pathname.startsWith('/api/og/')
    || pathname.startsWith('/sitemap')
    || /^\/[a-z]{2}(?:\/(event|leaderboard|activity)|$)/.test(pathname)  // locale prefixes
  )
}
```

```ts
// src/config/region-blocks.ts
export const RESTRICTED_COUNTRIES = new Set([
  // OFAC
  'CU', 'IR', 'KP', 'SD', 'SY', 'RU', 'BY',
  // Polymarket policy
  'US', 'JP', 'BE', 'SG',
  // Update from Polymarket TOS at launch eve (Phase 9 A5)
])
```

### Why `request.headers.get('x-vercel-ip-country')` is also OK

The headers are set automatically; you can read them directly without `geolocation()`. `geolocation()` is a thin wrapper that reads those headers and returns a typed object. Either works; `geolocation()` is the maintained API.

### Vercel `next.config.ts` `vercel.json` notes

Middleware in Next.js App Router doesn't need anything in `vercel.json`. It runs on the Edge runtime by default. The `matcher` config controls which paths trigger it.

## 3. Builder code in V2 Order struct + fee mechanism

### Updated finding from Polymarket fee docs (this session)

Verbatim quotes that resolve Phase 4 Finding 4:

> "Builders attach `builderCode` directly to orders—no separate fee field in the order body. The code becomes part of the signed V2 order struct and appears in onchain `OrderFilled` events for attribution and settlement."

> "Builder fees never replace platform fees — they're always additive."

> "Collected builder fees are distributed to the wallet associated with your builder profile."

### What this means concretely

1. **The current 12-field `EIP712_TYPES.Order` (`src/lib/constants.ts:47-62`) is the V1 struct.** V2 adds the builder field. To attach builder code, we sign a V2 Order, not V1.
2. **The exchange address `0x4bFb41d5B3570DeFd03C39a9A4D8dE6Bd8B8982E` may or may not be V2.** The Polymarket TS clob-client `config.ts` exposes a single `exchange:` per chain; if their SDK supports builder attribution then this IS V2. Live test ahead of impl.
3. **Domain `name` may have changed.** V2 may keep `'CTF Exchange'` or change to something like `'CTF Exchange V2'`. Get from on-chain `eip712Domain()` view function or the SDK.
4. **No separate fee skim in our app.** Polymarket calculates platform fee + builder fee at match time, settles on-chain, accrues to our `POLYMARKET_BUILDER_ADDRESS`. We do not need to do anything in our code beyond:
   - Set `feeRateBps` on the user's order (this is the protocol fee, Polymarket-level)
   - Attach `builderCode` (this is what triggers builder fee accrual at our configured rate)
   - Configure our `builder_taker_fee_bps` and `builder_maker_fee_bps` once via Polymarket builder dashboard

## 4. Admin: builder wallet + fee configuration UI

### What we need on /admin

A new admin route `/admin/builder` that mirrors what `polymarket.com/settings?tab=builder` does, scoped to our team. Fields:

| Field | Editable? | Storage | Reads from |
|---|---|---|---|
| Builder code (bytes32) | Read-only | env var `POLYMARKET_BUILDER_CODE` | env |
| Builder wallet address | Read-only | env var `POLYMARKET_BUILDER_ADDRESS` | env |
| Builder API key | Read-only / masked | env var `POLYMARKET_BUILDER_API_KEY` | env |
| Builder taker fee (bps) | Read-only display | Polymarket builder dashboard | live API call to `clob.polymarket.com/builder/profile` (TBD endpoint) |
| Builder maker fee (bps) | Read-only display | same | same |
| Lifetime builder revenue | Read-only display | `clob.polymarket.com/builder/trades` aggregated | Phase 10 A4 cron |
| Today's builder revenue | Read-only display | same | same |
| Top earning markets (last 7d) | Read-only display | aggregated from builder-trades table | Phase 10 A4 cron |

**Important: fees are NOT editable from our /admin.** They're set via Polymarket's dashboard. Our /admin DISPLAYS the current values (read from Polymarket) so admins can see what's active without leaving Axes.

If the user wants editable-from-Axes fees, that's an extra layer:
1. Add an admin-only "Update fees" form in `/admin/builder`.
2. The form POSTs to a new server action `updateBuilderFees({takerBps, makerBps})`.
3. The server action calls Polymarket's builder API endpoint that updates the rate (if such an endpoint exists publicly — the docs imply config goes through the dashboard UI; an HTTP API for it isn't documented).
4. If no public endpoint, we emit a deeplink `https://polymarket.com/settings?tab=builder` and let the admin click through.

**Recommendation: read-only display, deeplink to Polymarket for edits.** Saves us from reverse-engineering an undocumented endpoint.

A "test our builder code" tool: an admin clicks a button that places a tiny test order using the test wallet, and the page shows the trade arriving in our builder revenue table. This is the Phase 4 A8 live test, productized.

4. **Rate limits on Polymarket APIs**: We don't know Polymarket's rate limits. At launch with 1000 concurrent users, we could trip them. Plan: add a simple per-host `withCache` shim using our existing Upstash redis (already wired) for hot read endpoints (`/positions`, `/value`, `/v1/leaderboard`).
5. **Markets that exist on kuest but not Polymarket**: Today our DB has 100 events from kuest. Post-Phase 1 A1, gamma sync replaces them. But existing user positions + open orders on kuest-only markets get orphaned. Migration strategy: pre-cutover, snapshot user state on kuest; offer a withdraw flow; then cut over with empty-position users. Flag for Phase 11 cutover.

These five concerns are real but smaller than the main phases. They go into the cutover gate's "soak" checklist (Phase 11 Stage 5) rather than triggering a Phase 14.
