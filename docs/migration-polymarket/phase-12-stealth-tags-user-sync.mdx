# Phase 12. The "ready to ship" phase

## Why this phase exists

Phases 1-11 audit every consumer endpoint and propose changes. Five things
they didn't pin down hard enough:

1. A concrete wallet recommendation (Reown or Magic Link?), not a "decision documented".
2. The full surface where "Polymarket" could leak through to users — the
   user wants Polymarket invisible to end users, surfaced only as Axes.
3. Verified Polymarket Polygon mainnet contract addresses (Phase 4 A1 had
   the directional finding; this phase has the verbatim addresses).
4. Gamma `/tags` ingest details (Phase 1 covered events; tags need
   their own treatment).
5. Comment ingestion bringing user/wallet records along with it. Comments
   carry rich profile data; we can populate a local user mirror so the rest
   of the app reads from the DB instead of fanning out to gamma per render.

Out of scope: anything already covered in Phases 1-11. Phase 12 is the
"close the gaps" phase before merging starts.

## 1. Wallet recommendation

### The decision

**Keep Reown AppKit + Wagmi for the connector layer. Add Magic Link as an alternate sign-in method post-launch (Phase 5 A4).**

This is a recommendation, not just a documented choice. If the user picks Magic-only, see "Alternate path" below.

### Why keep Reown

| Argument | Detail |
|---|---|
| Already wired | `src/lib/appkit.ts` is set up; `AppKitProvider` wraps both `(platform)` and `admin` layouts; SIWE via `@reown/appkit-siwe` is integrated; the connect button is in the navbar and in conditional CTAs (`FilterToolbar.tsx:84`, `PublicPositionsList.tsx:1004`, etc.). Removing it touches 30+ files. |
| Multi-wallet coverage | Reown's modal supports MetaMask, Rabby, WalletConnect, Coinbase Wallet, Trust, Phantom, and 250+ others out of the box. Magic alone is email-only — power users on browser extensions get a worse experience. |
| Compatible with Polymarket builder pattern | `Polymarket/wagmi-safe-builder-example` is wagmi-first; our setup IS wagmi (Reown is a UI/connector layer on top). The reference impl drops in. |
| User-visible branding is minimal | Reown's modal has a small "Powered by Reown" footer. The Polymarket pattern uses Reown's Wagmi adapter behind the scenes; the UX user sees is "connect a wallet". No "Polymarket" or "Reown" text dominates. We can hide the footer with CSS if we want full Axes branding. |
| Magic Link adds value but as ADD-on | Email-only auth converts ~3x better than wallet-only for new users (Polymarket's own data per their builder docs). Adding Magic as a "Sign in with email" button alongside the connect modal is strictly better than choosing one. Phase 5 A4. |

### Why NOT Magic-only at launch

| Risk | Why it bites |
|---|---|
| Single auth path | If Magic has an outage, every user is locked out. Reown's wallet path is independent. |
| Power users dislike email auth for crypto | Existing wallet holders prefer their existing wallet over a new email-bound key. We'd lose conversion for that segment. |
| Reown removal cost | The 30+ file diff to rip Reown out adds risk to a launch we're trying to keep narrow. |
| Magic cost model | Magic is paid per active wallet (their pricing is per-MAU). Reown is free. At our launch scale this is small but it's an extra contract to negotiate. |

### Alternate path (if user overrides to Magic-only)

If the user explicitly picks Magic-only:

1. Replace `src/lib/appkit.ts` with `src/lib/magic.ts` per `Polymarket/magic-safe-builder-example`'s `lib/magic.ts`.
2. Replace `AppKitProvider.tsx` with a `MagicProvider.tsx` that wraps the app and exposes the Magic-derived signer.
3. Replace `useAppKit()` and `useAppKitAccount()` callers across 30+ files with a Magic-equivalent `useMagicAccount()`.
4. Drop `@reown/appkit*`, `@wagmi/connectors` overrides; add `@magic-sdk/admin`, `@magic-ext/oauth`, `magic-sdk`.
5. Switch `lib/auth.ts` (SIWE) to Magic's DID-token verification.

This is roughly 1 week of focused work and adds risk to launch week. Recommend NO — but it's the user's call.

### Hiding Polymarket from the wallet UX specifically

Whichever connector we pick, none of them surface "Polymarket" branding to the user. The wallet UX is Reown's or Magic's. Polymarket only enters the picture in the post-connect flow:

- Safe deployment shows the user a Safe transaction sign prompt (looks like a Safe modal, says "Confirm transaction in your wallet"). No Polymarket logo.
- Token approval shows ERC-20 `approve()` in the wallet. No Polymarket logo.
- L1 derivation shows the EIP-712 typed-data prompt (`ClobAuthDomain`/`ClobAuth`). The domain string says `ClobAuthDomain` not `Polymarket`. We can't change this string without breaking signature recovery.

**The one place "ClobAuthDomain" leaks**: the wallet's typed-data prompt screen. Modern wallets (MetaMask, Rabby) show the domain name to the user before they sign. They will see `ClobAuthDomain`. We can't rename it without breaking interop. **Mitigation**: the copy on our app's side ("This signature lets Axes trade on your behalf") can frame it; some users will still see the unfamiliar name and ask. Add a one-line FAQ entry.

Field meanings (inferred from data + sample):

- `id`: integer string, primary key.
- `label`: human-readable name.
- `slug`: URL-safe identifier.
- `forceShow`: tag is pinned in navigation regardless of recent activity.
- `forceHide`: tag is suppressed from default UI even when active.
- `isCarousel`: tag appears in the homepage carousel selector.
- `publishedAt`/`createdAt`/`updatedAt`: standard timestamps.
- `requiresTranslation`: copy-translation gate.
- `updatedBy`: admin user id (foreign).

### Filter knobs we should use

- `?limit=N&order=updatedAt&ascending=false` — most-recent first.
- `?is_carousel=true` — carousel-eligible only.
- `?include_template=true` — include template-only tags (not used in our flow).
- `?force_show=true` — only pinned tags.

### `/events?tag_slug=X` for tag-filtered event listings

`GET /events?tag_slug=politics&limit=N` and `GET /events/keyset?tag_slug=politics&limit=N` both work (live-verified). This is what the navbar's "Politics" link should hit, instead of querying our own DB by joined tag.

### Tag ingest plan

The Phase 1 gamma sync already pulls events with their tags inline (gamma's `/events/keyset` includes a `tags` array per event). This populates our `event_tags` join table.

What's MISSING:

1. **Standalone tag sync**. We need a `/api/sync/tags` cron that pulls `/tags` directly. Why: gamma's event-embedded tag list only contains tags that appear on at least one event. Tags that exist but are empty (newly created, all events resolved) are not surfaced. Without a standalone sync, our navigation lacks pinned tags (`forceShow=true`) that have no live events.
2. **Tag config columns**. Our `tags` table needs `force_show`, `force_hide`, `is_carousel`, `published_at` columns to drive the home navigation. Currently we only have `slug`, `label`, `created_at`, `updated_at` (Phase 1's mapper drops the rest).
3. **Tag → carousel rendering on home**. Today our home carousel uses an admin-curated list. Adopt Polymarket's `is_carousel=true` set to drive our home carousel instead — fewer manual ops.

## 5. Comment + user/wallet sync

### What comments give us per row

```json
{
  "userAddress": "0x605e6fd2aab5827fa88f8e5f640f9f76b97e3c34",
  "profile": {
    "name": "thiagofelipe",
    "pseudonym": "Bronze-Corporation",
    "displayUsernamePublic": true,
    "bio": "",
    "proxyWallet": "0xda25452547d537e7196e2655b31773c5fc3babaf",
    "baseAddress": "0x605e6fd2aab5827fa88f8e5f640f9f76b97e3c34"
  }
}
```

That's a complete user identity record:

- `baseAddress` — the EOA the user actually controls.
- `proxyWallet` — the Safe address that holds funds and trades.
- `name` — Polymarket-stored display name (when public).
- `pseudonym` — Polymarket-assigned pseudonymous handle (the "Bronze-Corporation" style).
- `displayUsernamePublic` — whether to show `name` or `pseudonym`.
- `bio` — user-stored bio.

Activity (data-api `/activity`) carries the same `pseudonym`, `name`, `profileImage`, `profileImageOptimized`. Holders carries the same. Leaderboard carries the same. Every Polymarket data source we hit can populate a user mirror.

### Why a local user mirror matters

- **Avatar/name lookup latency**: today `useUserProfile`-style hooks (if we have any) would round-trip to gamma per render. With a local mirror, it's a join.
- **Cross-page consistency**: same user appearing in comments, activity, holders, and leaderboard renders the same name/avatar from one source.
- **Notification routing later**: Phase 10 A5's referral payouts need a user lookup by address. A populated mirror makes that lookup local.

### Schema: `polymarket_users` table

New columns / new table (decide at impl time):

```sql
CREATE TABLE polymarket_users (
  base_address       TEXT PRIMARY KEY,           -- normalized lowercase
  proxy_wallet       TEXT,                       -- normalized lowercase, NULLable until known
  pseudonym          TEXT,
  name               TEXT,
  display_username_public BOOLEAN,
  bio                TEXT,
  profile_image      TEXT,
  profile_image_optimized TEXT,
  first_seen_at      TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  last_seen_at       TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  source             TEXT NOT NULL  -- 'comments', 'activity', 'holders', 'leaderboard'
);

CREATE INDEX polymarket_users_proxy_wallet_idx ON polymarket_users (proxy_wallet);
```

Why `polymarket_users` is separate from our existing `users` table:
- `users` is for wallet holders who have authenticated to Axes (have a session, may have created markets, have settings).
- `polymarket_users` is the read-mirror of any Polymarket address we've ever observed in our data feeds — most of them have no Axes account.
- Joining: when an Axes user authenticates, we look up `polymarket_users WHERE base_address = users.address` to copy over the pseudonym/avatar/bio without forcing them to re-enter.

### Sync triggers

Three places we observe user data; each writes to `polymarket_users` opportunistically:

1. **Comments fetch** (Phase 7 A1): every comment we read has `profile.{...}` — write through to the mirror.
2. **Activity feed read** (`usePublicActivityQuery`, `event-activity`): every row carries profile fields — write through.
3. **Holders read** (`fetchTopHoldersFromDataApi`): every holder has profile fields — write through.

All three are read paths; we add a low-priority background write to the mirror on response. Cheap. Postgres `INSERT ... ON CONFLICT ... DO UPDATE SET last_seen_at=...` for upserts.

### NO standalone "sync all Polymarket users" cron

We DO NOT proactively crawl Polymarket for users. Two reasons:

1. Polymarket has 100k+ traders; full crawl is rude and costly.
2. Opportunistic accumulation gives us exactly the users our app actually surfaces — no over-collection.

If we ever need a specific user's profile and they're not in our mirror, we hit gamma's profile-by-address endpoint on-demand and cache.

### Wallet provenance: why baseAddress is the PK, not proxyWallet

A user has one base EOA but can have multiple Safes over time (theoretical). The base address is the durable identity. `proxyWallet` is a property that happens to be the user's currently-active Safe.

When ingesting from sources that only give us `proxyWallet` (e.g. holders responses don't always carry baseAddress), we treat that as a partial record and let later observations enrich it.

## Risks specific to Phase 12

1. **Comment-author privacy.** Polymarket's `displayUsernamePublic=false`
   profiles render with pseudonyms; we must respect this flag in our
   display logic. If we accidentally surface `name` for a private user,
   we leak data. Mitigation: a single `getDisplayName(profile)` helper
   that branches on the flag — never render `name` directly.

2. **Mirror table grows unbounded.** Every comment we surface adds a row.
   At launch scale this is fine (thousands of users). At Polymarket scale
   it's still small (hundreds of thousands). Mitigation: add a periodic
   cleanup that drops mirror rows not touched in 90 days, IF we never want
   to reuse them. Defer this concern until rows exceed 500k.

3. **Address case normalization.** Ethereum addresses are case-insensitive
   functionally but checksummed for display. The mirror MUST normalize to
   lowercase on insert and compare lowercase on lookup; otherwise we'll
   double-row the same user.

4. **A5 fire-and-forget swallows errors.** If the mirror table gets out of
   sync because a write silently failed, we'd never know. Mitigation: log
   write failures with a counter and Sentry-track if rate exceeds 1% of
   reads.
