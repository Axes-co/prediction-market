# Phase 2. Pricing + charts (CLOB read-only)

## Scope

Read paths from the frontend to the CLOB for everything price-shaped: book
summaries, mid/bid/ask quotes, last trade prices, batch and singular price
history, and the volume figure that backs the "$X Vol." line on cards and the
chart header. This phase wires the frontend onto Polymarket's actual response
contracts (now that `CLOB_URL=https://clob.polymarket.com`) without changing
write paths.

Out of scope here: order placement and signing (Phase 4), websockets that push
incremental book updates (Phase 6), the spread display (touched only as a
note), and any user-scoped read like positions or open orders (Phase 3).

## Findings

### Finding 1. `/data/volumes` is also called from three frontend components, not just the cron

**Claim.** The Phase 1 finding 2 only enumerated the cron (`sync/volume/route.ts:306`) for the broken `/data/volumes` POST. There are three more sites in the rendered app that hit the same dead URL every 60 seconds while a user is on the page.

**Evidence.**

- `src/app/[locale]/(platform)/event/[slug]/_components/MarketOutcomeGraph.tsx:518`
  ```ts
  const response = await fetch(`${process.env.CLOB_URL}/data/volumes`, {
    method: 'POST', ...
    body: JSON.stringify({ include_24h: false, conditions: volumeRequestPayload.conditions }),
  })
  ```
- `src/app/[locale]/(platform)/event/[slug]/_components/EventMetaInformation.tsx:48` — same pattern.
- `src/app/[locale]/(platform)/event/[slug]/_components/EventMarketCard.tsx:58` — same pattern.
- Live probe (this session): `POST clob.polymarket.com/data/volumes` → HTTP 404 "page not found".
- Each `useQuery` is configured with `staleTime: 60_000, refetchInterval: 60_000`, so each open event page makes 1 request/min that always 404s.

**Impact.** The fallback path in each component is `event.volume` / `market.volume` (the gamma-populated DB column, which Phase 1 finding 3 confirmed already updates every 10 minutes). So the visible volume number is correct. But every client visiting an event page is opening 1 (or 2 for `MarketOutcomeGraph` rendered N times) failed network requests per minute. This produces console-network noise, fills server logs with 404 echoes, and devtools shows "trade-volumes" red entries for every visit.

**Confidence.** High. Direct probe + three identical call sites in the source.

### Finding 2. `/batch-prices-history` rejects bounded requests that omit `interval`; two of our three branches do exactly that

**Claim.** Polymarket's `POST /batch-prices-history` requires `interval` regardless of whether `startTs`/`endTs` are present. The error string is misleading ("please use 'startTs' and 'endTs' or 'interval'") because all three of the bounded-without-interval shapes I tested were rejected. The matching singular `GET /prices-history` accepts startTs+endTs without `interval`, so the requirement is endpoint-specific.

`useEventPriceHistory.ts` builds three filter shapes (after the in-progress ALL-range fix at lines 103-114). Two of those shapes still send bounds without `interval` and will fail on Polymarket:

- Active markets, `isLongRange && ageSeconds < windowSeconds` (lines 124-128): emits `{fidelity, startTs, endTs}`.
- Resolved markets, non-ALL range (lines 144-148): emits `{fidelity, startTs, endTs}`.

**Evidence.**

- Live probe (this session):
  - `POST /batch-prices-history` body `{markets, fidelity:30, startTs, endTs}` → 400, error string above.
  - `POST /batch-prices-history` body `{markets, fidelity:30}` → same error.
  - `POST /batch-prices-history` body `{markets, interval:"1d", fidelity:5, startTs, endTs}` → 200, 288 points within bounds.
- Code: `src/app/[locale]/(platform)/event/[slug]/_hooks/useEventPriceHistory.ts:122-148` (the two failing branches), and `src/app/[locale]/(platform)/event/[slug]/_utils/priceHistoryApi.ts:54-76` (`buildBatchPriceHistoryRequestBody`, which only passes through whatever `RangeFilters` contains).

**Impact.** A user looking at a chart on either (a) a brand-new market younger than the selected long range or (b) any resolved market sees "Failed to fetch price history" thrown inside `fetchBatchPriceHistoryByTokenIds` (caught by the per-chunk try/catch at line 117), which empties the chart for that token. The fallback `[HERO_CHART_DEBUG]` `console.error` would surface this in dev. In production, the chart silently shows a flat line built from `lastKnownPrice`-only paths, or no data at all if no chunk succeeds.

**Confidence.** High. Direct probe of every relevant body shape, source lines cited.

### Finding 3. The new `buildClobPriceQueryEntries` helper is necessary, not stylistic

**Claim.** `POST /prices` and `POST /last-trades-prices` on Polymarket return BUY-only or SELL-only data when called unsided (`[{token_id}]`). The new helper at `src/lib/clob.ts:21-23` that expands each token into both `{token_id, side:"BUY"}` and `{token_id, side:"SELL"}` is the only correct shape if the caller wants both sides.

**Evidence.**

- Live probe `POST /prices` body `[{"token_id":YES}]` → `{"YES":{"SELL":"0.154"}}`. BUY missing.
- Live probe `POST /prices` body `[{token,"side":"BUY"},{token,"side":"SELL"}]` → `{"YES":{"BUY":"0.153","SELL":"0.154"}}`.
- Existing call sites that consume both sides:
  - `useEventMidPrices.ts:30-43` constructs midpoint from both BUY (best ask) and SELL (best bid). Without sided entries, BUY would be undefined, the midpoint would degrade to `bid` only, and the chance/odds derivation in `buildChanceByMarket` would skew low.
  - `lib/db/queries/event.ts:295-307` consumes both sides for `OutcomePrices`.
  - `EventOrderBookUtils.ts:28` reads BUY as last trade for buy and SELL for sell. Same logic.

**Impact.** Without the helper (i.e. if someone reverts to `[{token_id}]`), event cards' midpoint, chance, and "Yes/No" highlights would visibly mismatch the order book by half the spread. This is the kind of regression that's easy to ship and hard to spot in QA because the numbers are still "near right".

**Confidence.** High. Direct probe of both shapes against Polymarket production.

### Finding 4. `/prices-history` (singular) and `/batch-prices-history` (batch) have different request contracts; embed and OG paths use the singular and are unaffected

**Claim.** Singular GET `/prices-history?market=&fidelity=&startTs=&endTs=` accepts startTs+endTs without `interval`, returns the same `{history:[{t,p},…]}` shape, and is what `src/lib/embed-chart.ts:81` and `src/app/api/og/event/route.tsx:354` use. Both call sites work as-is on Polymarket.

**Evidence.**

- Live probe `GET /prices-history?market=YES&fidelity=30&startTs=…&endTs=…` → 200, 337 points.
- Code: `embed-chart.ts:81-96` (server-side, used for embed widget), `route.tsx:348-386` (OG SVG generator).
- Both wrap the call in `{ next: { revalidate: 60-300 } }` and a try/catch returning `[]` — failure mode is graceful even if the contract drifts.

**Impact.** No action needed in Phase 2 for embeds or OG. We just want to be sure the divergence is documented so a future "consolidate everything onto batch" refactor doesn't accidentally break OG.

**Confidence.** High.

### Finding 5. `/spreads` works (POST) but `/spread/<token>` 404s; Polymarket exposes spread via batch only

**Claim.** Polymarket has a `POST /spreads` endpoint (live-probed) that returns `{token_id: spread_string}` for a list of tokens. There is no singular `/spread/<id>` route. We currently derive spread on the client from `bestAsk - bestBid` in `buildOrderBookSnapshot` (`EventOrderBookUtils.ts:88-90`) and ignore the `summary?.spread` field that exists in `OrderBookSummaryResponse` (`EventOrderBookTypes.ts:36`). That's fine functionally but means we're computing something the server can give us authoritatively.

**Evidence.**

- Live probe `GET /spread/<token>` → 404.
- Live probe `POST /spreads` body `[{token_id}]` → `{"4394…080":"0.001"}`.
- Code: `EventOrderBookTypes.ts:36` declares the `spread` field but no consumer reads it from a response (`EventOrderBookUtils.ts:88-90` always derives locally).

**Impact.** Low. Optional optimization for Phase 6 (when websockets push deltas — having server-confirmed spread avoids one source of drift). No Phase 2 action.

**Confidence.** High.

## Risks

1. **A1 silent miss on a fourth filter shape.** `buildTimeRangeFilters` has three branches today. If a future range is added without going through the helper, it could re-introduce the bounded-no-interval bug. The proposed unit test in A1 sweeps every existing branch; we should keep that test as a regression guard rather than letting it become a one-shot.

2. **A2 fallback arithmetic.** Each of the three components currently does `Number.isFinite(volumeFromApi) ? volumeFromApi : event.volume`. After A2, they should just use `event.volume` directly. Watch for components that do additional aggregation (`MarketOutcomeMetaInformation` totals across markets) where the previous code might have summed status-200 entries differently than the DB-populated single number. Fast check: pick one event and confirm displayed total matches `events.volume` column, not the per-market sum.

3. **A1 widens the chart cache key surface.** Adding `interval` to bounded shapes changes the body hash if anyone is keying request caches by stringified body. Our React-Query key (`useEventPriceHistory:296`) keys on `range`, not body, so this is fine internally — but the upstream Cloudflare/Vercel CDN cache (if any) keys on URL only, and `/batch-prices-history` is POST so no CDN cache applies. No actual risk; flagging because this is the kind of thing that bites two phases later.

4. **A4 removed too eagerly.** If A1 ships and the bounded path is still subtly broken (e.g. on a new event with no trade history at all), the removed instrumentation is exactly what would have surfaced the bug. Safer ordering: A1 → wait for at least one production deploy cycle → A4.
