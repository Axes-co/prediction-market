# Phase 1. Markets, events, tags ingestion

## Scope

This phase covers the read-and-store pipeline for the canonical entities the
frontend renders on every page: events, markets, conditions, outcomes, tags
(and their sport metadata, where applicable). It includes:

- Gamma sync code (`src/lib/gamma/*`) and its cron route
- The five `/api/sync/*` cron routes that touch market/event/tag state
- The DB schema columns those crons read from / write to
- The Event/Market/Outcome/Tag types the frontend relies on

Out of scope here: trading endpoints (Phase 2-4), comments (Phase 7),
translations beyond noting they exist (Phase 1 confirms they're independent of
the kuest→Polymarket switch).

## Findings

### Finding 1. Gamma client pagination is broken (wrong cursor param name)

**Claim.** `src/lib/gamma/client.ts:46` sends `next_cursor=<cursor>` on
follow-up keyset pages. Polymarket's `/events/keyset` ignores this param and
returns page 1 again. The correct param name per spec is `after_cursor`.

**Evidence.**

- Code: `src/lib/gamma/client.ts:45-47`
  ```ts
  if (cursor) {
    params.set('next_cursor', cursor)
  }
  ```
- Spec quote (`list-events-keyset-pagination.md`): "after_cursor: Opaque cursor
  token from a previous response's next_cursor".
- Live probe (this session): both `next_cursor=<c>` and `after_cursor=<c>`
  hit on the same cursor. With `next_cursor`, page 2's first slug equals page
  1's first slug (`democratic-presidential-nominee-2028`). With `after_cursor`,
  page 2's first slug is different (`republican-presidential-nominee-2028`).

**Impact.** Every gamma-sync cron run only ingests the first 100 events
(`DEFAULT_PAGE_SIZE` from `client.ts:14`). The DB never sees pages 2+. Our DB
currently shows 100 events, which matches this exact ceiling. Our market
catalog is one page deep, not the full Polymarket catalog (currently ~30k
events).

**Confidence.** High. Live probe demonstrated the broken behavior, the fix
matches the spec, and 100 events in our DB matches the page-size ceiling.

### Finding 2. Volume sync calls a non-existent endpoint

**Claim.** `src/app/api/sync/volume/route.ts:306` POSTs to
`${CLOB_URL}/data/volumes`. This endpoint does not exist on Polymarket native
(neither on `clob.polymarket.com` nor on `data-api.polymarket.com`). The cron
fails silently every 10 minutes after the env switch.

**Evidence.**

- Code: `src/app/api/sync/volume/route.ts:306-311`
  ```ts
  const response = await fetch(`${CLOB_URL}/data/volumes`, {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify(payload),
    ...
  })
  ```
- Live probe (this session) `POST clob.polymarket.com/data/volumes` → HTTP 404
  "page not found". `POST data-api.polymarket.com/data/volumes` → HTTP 404.
- Polymarket's published equivalent is `GET data-api.polymarket.com/live-volume
  ?id=<event_gamma_integer_id>`, response is per-event aggregate.

**Impact.** Volume figures on the homepage cards, sorting, and the
"is_trending" derivation become stale. Frontend reads stale `markets.volume`
and `markets.volume_24h` columns, currently populated only by the gamma sync
(`mapper.ts:195-196` reads `volumeClob` and `volume24hrClob`). The cron is
pure waste with the new env.

**Confidence.** High. Direct probe; both hosts return 404.

### Finding 3. Volume data is already populated by gamma sync (volume cron is now redundant)

**Claim.** `mapper.ts:195-196` already maps gamma's `volumeClob` and
`volume24hrClob` into our `volume` and `volume_24h` columns on every
market upsert. So the volume cron's purpose is already covered by the gamma
cron, except for finer-grained refresh between gamma runs.

**Evidence.**

- Code: `src/lib/gamma/mapper.ts:195-196`
  ```ts
  volume: decimalString(gammaMarket.volumeClob ?? gammaMarket.volume),
  volume24h: decimalString(gammaMarket.volume24hrClob ?? gammaMarket.volume24hr),
  ```
- Repo schema: `markets.volume`, `markets.volume_24h` are written by
  `repository.ts:233-234` from these mapped fields.
- Gamma keyset event response includes both fields plus `volume1wk`,
  `volume1mo`, `volume1yr`, `liquidity`, `liquidityClob`, `openInterest` per
  event, which our mapper currently drops.

**Impact.** With gamma running every 10 minutes (`vercel.json:11`), our market
volumes update at gamma cadence. We could either (a) delete the volume cron, or
(b) keep a fast volume refresh by switching it to `data-api/live-volume`
(per-event aggregate). Option (a) is simpler and matches what the data layer
already does.

**Confidence.** High.

### Finding 4. Mapper drops several gamma fields that the frontend would benefit from

**Claim.** Gamma's keyset event response carries 50 fields. Our mapper
(`mapper.ts:73-200`) consumes ~15 of them. Several useful fields are dropped.

**Evidence.** Gamma response keys (live probe, this session):

```
['active','archived','automaticallyActive','closed','commentCount',
 'competitive','countryName','createdAt','creationDate','cumulativeMarkets',
 'cyom','deploying','deployingTimestamp','description','electionType',
 'enableNegRisk','enableOrderBook','endDate','estimateValue','eventMetadata',
 'featured','featuredOrder','gmpChartMode','icon','id','image','liquidity',
 'liquidityClob','markets','negRisk','negRiskAugmented','negRiskMarketID',
 'new','openInterest','pendingDeployment','requiresTranslation','resolutionSource',
 'restricted','showAllOutcomes','showMarketImages','slug','sortBy','startDate',
 'startTime','tags','ticker','title','updatedAt','volume','volume1mo','volume1wk',
 'volume1yr','volume24hr']
```

Currently consumed by our mapper: `slug`, `title`, `description` (as `rules`),
`icon`, `image`, `enableNegRisk`, `negRiskAugmented`, `negRisk`,
`showAllOutcomes`, `showMarketImages`, `startDate`, `endDate`, `createdAt`,
`tags`, `markets`. Currently dropped: `commentCount`, `competitive`, `cyom`,
`featured`, `featuredOrder`, `liquidity`, `liquidityClob`, `negRiskMarketID`,
`openInterest`, `requiresTranslation`, `restricted`, `ticker`, `volume1wk`,
`volume1mo`, `volume1yr`, `eventMetadata`, `electionType`, `gmpChartMode`,
`countryName`, `automaticallyActive`, `enableOrderBook`, `sortBy`, `startTime`.

**Impact (graded).**

- High-value (touch in this phase if cheap): `negRiskMarketID` (mapped to
  `events.neg_risk_market_id`, frontend uses it in `EventContent.tsx:602` for
  position composition), `commentCount` (drives comment badge on cards),
  `restricted` (geoblock; Phase 9), `liquidity` (sort key), `featured`
  (curation), `requiresTranslation` (gates Phase 1's translation cron).
- Medium-value: `volume1wk`/`1mo`/`1yr` (timeframe sorts), `openInterest`,
  `electionType`, `competitive`.
- Low-value/cosmetic: `gmpChartMode`, `eventMetadata`, `countryName`.

**Confidence.** High for the field list; medium for the impact grading until
each consumer site is verified.

### Finding 5. Three cron routes are independent of the kuest→Polymarket switch

**Claim.** The following crons are unaffected by the env swap and require no
Phase 1 action:

- `events/route.ts`: pulls from Goldsky public subgraph indexing the same
  Polygon CTF contracts Polymarket uses. The subgraph URL is hardcoded
  (`route.ts:26`) and is not behind kuest. Continues to work.
- `resolution/route.ts`: same pattern, different Goldsky subgraph
  (`route.ts:18`), reading UMA OOv2 resolution state on Polygon. Continues to
  work.
- `translations/route.ts`: OpenRouter LLM jobs. No backend service swap is
  involved.

**Evidence.** Hardcoded URLs in the route files cited above. No reference to
`process.env.CLOB_URL`, `RELAYER_URL`, or `GAMMA_URL` in the bodies of those
three files.

**Impact.** No-op for Phase 1. Re-evaluate `events/route.ts` overlap with
gamma in Phase 8 (Cron jobs and admin sync).

**Confidence.** High.

### Finding 6. Outcomes table primary key is `token_id`, which collides across gamma re-syncs of resolved markets

**Claim.** `outcomes.token_id` is declared `PRIMARY KEY` at
`src/lib/db/schema/events/tables.ts:390`. The repository upsert at
`repository.ts:251-256` uses `onConflictDoNothing({ target: outcomes.token_id })`.
Polymarket reuses `token_id` per `(condition_id, outcome_index)` so the PK is
correct in principle. But `onConflictDoNothing` means once an outcome row
exists, subsequent gamma reads cannot update `outcome_text` rewordings or
correct `outcome_index` swaps. We don't observe this in practice today, but
it's worth flagging for Phase 8.

**Evidence.** Schema: `tables.ts:390` `token_id: text().notNull().primaryKey()`.
Repo: `repository.ts:251-256`.

**Impact.** Low (Polymarket rarely reorders outcomes mid-market). Keep the
finding as a known limitation; address only if it surfaces.

**Confidence.** Medium. Limitation is real per the code, but production impact
is observational and low.

## Risks

1. **A1 will trigger a much larger ingest.** Today we have 100 events.
   Post-fix we may pull tens of thousands of pages. Mitigations: keep
   `DEFAULT_TIME_LIMIT_MS = 250_000` from `sync.ts:54`, keep keyset
   `pageSize` at 100 (default in `client.ts:14`), and ensure
   `acquireGammaSyncLock` (15-min staleness) prevents overlapping runs.
   Do the first run manually with `?maxPages=10` to inspect throughput
   before letting the cron loose.

2. **A2 deletion changes which fields update.** Today, even though the volume
   cron 404s on Polymarket, removing it changes the failure mode (silent 404
   → no cron at all). If anyone is relying on the cron's mere existence for
   liveness alerting, that signal goes away. Mitigation: announce in the
   migration changelog.

3. **Schema additions in A3/A4 require a migration deploy.** Per
   `vercel.json:3`, the build command runs `npm run db:push` first. So the
   migration applies on deploy, not in advance. This is the project's
   convention; just verify the migration is non-destructive (additive only).

4. **DB scale on first ingest after A1.** Outcomes table will grow ~50x to
   ~250k rows. Conditions and markets similarly. Verify Supabase plan limits
   before merging A1 to main.

## Status when phase is closed

Phase 1 is closed when:

- [ ] A1 merged. Gamma cron has run at least three full ticks against the
      fixed cursor. DB row counts: `events > 5000`, `markets > 50000`,
      `outcomes > 100000`.
- [ ] A2 merged or explicitly deferred with reason logged.
- [ ] A3 merged. `events.neg_risk_market_id` populated for ≥ 90% of
      `enable_neg_risk=true` events.
- [ ] A4 deferred to Phase 9 OR merged.

Then move to Phase 2 (pricing + charts read path) which requires the
populated event corpus this phase produces.
