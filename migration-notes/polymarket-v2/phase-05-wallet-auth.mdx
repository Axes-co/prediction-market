# Phase 5. Wallet + auth strategy

## Scope

Decide what stays of our current Reown AppKit + Wagmi + custom proxy wallet
flow vs what gets replaced by Polymarket's published patterns. Specifically:

1. Wallet connect surface (Reown AppKit modal, RainbowKit, ConnectKit, Magic
   Link email auth, Turnkey embedded wallet)
2. EOA → Safe (Gnosis Safe) derivation and deployment
3. Token approvals batched via Safe
4. User API credential derivation (L1 → L2 from Phase 4 A3) folded into the
   onboarding flow

Out of scope here: order signing — Phase 4; relayer endpoint adaptation —
Phase 4 A5; new-user UX copy — design, not engineering.

## Polymarket reference reading log

Live-fetched this session.

### `Polymarket/wagmi-safe-builder-example`

Pattern exactly matches what we want for our existing Reown/Wagmi base:

> 1. Wallet Connection → User connects EOA via browser extension (MetaMask, Rabby) through wagmi
> 2. Safe Derivation → Deterministically derive Safe address from EOA
> 3. Safe Deployment → Deploy Safe proxy via RelayClient with builder credentials
> 4. API Credentials → Obtain User API Credentials through temporary ClobClient
> 5. Token Approvals → Set USDC.e and outcome token approvals via batch transactions
> 6. Authenticated Trading → Initialize persistent ClobClient with builder config for order placement

Key files (per WebFetch this session):

- `providers/TradingProvider.tsx` — consolidates trading session and client state
- `providers/WalletProvider.tsx` — wraps wagmi into ethers + viem clients
- `hooks/useTradingSession.ts` — orchestrates full initialization flow
- `hooks/useRelayClient.ts` — RelayClient setup with builder authentication
- `hooks/useClobClient.ts` — authenticated CLOB client initialization
- `app/api/polymarket/sign/route.ts` — server-side **remote signing** endpoint (HMAC signing for builder creds stays server-side)
- `utils/approvals.ts` — token approval transaction builders

### `Polymarket/magic-safe-builder-example`

Same flow, different EOA source:

> Users log in via Magic Link's email-based interface, which provisions a non-custodial EOA wallet through Magic's TKMS (TEE Key Management System). No browser extension required.

Crucial detail:

> Builder credentials stay server-side for security. The `/api/polymarket/sign` endpoint handles HMAC signature generation using the builder's API key and secret. This "remote signing" pattern keeps sensitive credentials protected while enabling order attribution.

### `Polymarket/turnkey-safe-builder-example` and `Polymarket/magic-proxy-builder-example`

Variants of the same five-step onboarding with different EOA sources (Turnkey
embedded wallet, Magic with a minimal proxy instead of Safe). Architecturally
the same: connect EOA → derive proxy → deploy proxy → derive API creds →
approve tokens → trade.

### Existing builder SDKs (referenced by all four examples)

- `@polymarket/clob-client` — order signing, CLOB API auth, builder code field
- A `builder-relayer-client` package (referenced in the magic-safe README; exact npm name to be confirmed at implementation time when wiring) — Safe deploy + token approval batch tx + builder-attributed relayer flow

## Findings

### Finding 1. Our Reown AppKit + Wagmi setup is compatible with the wagmi-safe-builder pattern with no wallet-layer changes

**Claim.** The reference `wagmi-safe-builder-example` is built on the same wagmi `Config` shape we already use (`@wagmi/core@2.x`). Reown AppKit is a UI/connector layer on top of wagmi; it does not preclude using `WalletProvider` to extract `viem` and `ethers` clients from the wagmi context. We can keep AppKit as the modal and connector store.

**Evidence.**

- Code: `src/lib/appkit.ts:1-16` constructs `wagmiAdapter.wagmiConfig` which is a standard wagmi `Config`.
- Reference impl: `providers/WalletProvider.tsx` in `wagmi-safe-builder-example` derives ethers + viem clients from the wagmi `useWalletClient()` hook output. This works on top of any wagmi-compatible connector store, including Reown AppKit's.

**Impact.** No need to remove `@reown/appkit-*`. The wallet UX (the open-modal-and-connect flow that's already integrated into the navbar and the FilterToolbar) stays as-is. We add the post-connect onboarding shim (Steps 2-6) without touching connector code.

**Confidence.** High. The wagmi-safe-builder is wagmi-only by design.

### Finding 2. Drop the kuest "proxy wallet" model; adopt Polymarket's Safe proxy

**Claim.** Our current `proxy-wallet.ts` flow constructs a proprietary kuest proxy via the kuest relayer. That proxy is not a Safe. Replacing it with a Safe (per the reference impls) is required because Polymarket's relayer expects to be deploying a Safe at a deterministic address; calling Polymarket's relayer with our kuest-style proxy address will deploy a contract whose ownership semantics don't match Polymarket's order-routing assumptions.

**Evidence.**

- Code: `proxy-wallet.ts:147-178` posts to `${RELAYER_URL}` with custom headers; the response stores a `proxy_wallet_address` we treat as opaque.
- Reference: all four Polymarket builder examples deploy a **Safe** specifically; the on-chain account that holds USDC.e and outcome tokens is a Safe.

**Impact.** Hard blocker for trading on Polymarket. Existing kuest-proxy users have no migration path — they are isolated to the kuest exchange. Our existing user base on the Axes side is small enough that this migration cost is acceptable; if it weren't, we'd need a one-time withdraw flow to move funds from kuest proxy → user EOA → Safe.

**Confidence.** High.

### Finding 3. Builder credentials live server-side; the server-side `/api/polymarket/sign` endpoint is the canonical pattern

**Claim.** The four reference impls all keep `POLYMARKET_BUILDER_API_KEY` and `POLYMARKET_BUILDER_API_SECRET` strictly server-side. A small `/api/polymarket/sign` route generates the HMAC signature for any client request that needs builder-attributed auth. Our existing server-side `_actions/*.ts` model is already aligned with this — we do server-side HMAC for all CLOB writes today (via `buildClobHmacSignature`).

**Evidence.** Reference impl quote (verbatim): "Builder credentials stay server-side for security. The `/api/polymarket/sign` endpoint handles HMAC signature generation using the builder's API key and secret."

Our existing pattern (`store-order.ts:312-322`) does HMAC server-side, matching this constraint.

**Impact.** Low new work. Most files we'd need to add are already analogous to ones we have.

**Confidence.** High.

### Finding 4. Magic Link / Turnkey are optional add-ons, not required for launch

**Claim.** Magic Link (email-only auth) and Turnkey (passkey/embedded wallet) are alternative EOA sources for users who don't have a browser-extension wallet. Polymarket itself ships all three; users pick whichever they prefer. Our launch can ship with Reown's wallet modal alone (which already covers MetaMask, Rabby, WalletConnect, Coinbase, etc.) and add Magic Link as a follow-up post-launch.

**Evidence.** The pattern in all four reference impls is identical except for the EOA source. Hot-swapping EOA sources is supported by design.

**Impact.** Pre-launch work is constrained to the wagmi-flavored path. Magic Link is a Phase 11+ enhancement.

**Confidence.** High.

### Finding 5. The TradingOnboardingProvider's two-step "SafeProxy create → TradingAuth derive" sequence maps cleanly onto the reference flow

**Claim.** The reference's six-step flow can be folded into our existing onboarding state machine without restructuring it. The mapping:

| Reference step | Our equivalent |
|---|---|
| 1. Connect wallet | AppKit modal (existing) |
| 2. Derive Safe address | New: `useSafeDeployment().deriveSafeAddress(eoa)` |
| 3. Deploy Safe via RelayClient | `proxy-wallet.ts` (Phase 4 A5 rewrite) |
| 4. L1 → L2 API creds | `_actions/trading-auth.ts` (Phase 4 A3 rewrite) |
| 5. Token approvals (batch) | `_actions/approve-tokens.ts` (Phase 4 A5 rewrite) |
| 6. Persistent ClobClient | Already implicit in our `auth.clob.{key,secret,passphrase}` storage |

**Impact.** Phase 5 doesn't need new state machinery — Phases 4 A3 and 4 A5 already capture the bulk of the work. Phase 5 is mostly the SDK-adoption + naming-cleanup phase.

**Confidence.** High.

## Action items

### A1. Adopt `@polymarket/clob-client` and the builder-relayer-client SDK (P0)

- **Change.**
  i. `npm install @polymarket/clob-client` (verify exact name; might be `@polymarket/sdk`).
  ii. Identify and install the builder-relayer-client. The four reference repos all use it; the package name is referenced in their package.json — confirm at implementation time.
  iii. Initialize the CLOB client in a new `src/lib/polymarket/clob-client.ts` with the builder code from `process.env.POLYMARKET_BUILDER_CODE` (already in `.env.local` per Phase 0).
  iv. Replace bespoke fetch + HMAC code paths in `_actions/store-order.ts`, `_actions/cancel-*.ts`, `_actions/trading-auth.ts` with SDK calls. Keep server-side HMAC signing for the `/api/polymarket/sign` style remote signing pattern; do not move builder secrets to the client.
- **Why.** Adopting the SDK (a) reduces our hand-rolled code that has to track Polymarket's contract drift, (b) gets builder code attribution correct without us having to puzzle out the JSON body shape (Phase 4 Finding 4 open question), (c) shaves significant code from `_actions/*.ts`.
- **Test.**
  1. Place a test order via the SDK; confirm it lands at `clob.polymarket.com/order` with our builder code.
  2. Run `vitest run` after the migration; existing order-flow tests should pass with thin shims around the SDK.
- **Files.** Add `src/lib/polymarket/clob-client.ts`, `src/lib/polymarket/relay-client.ts`. Refactor the four `_actions/*.ts` files cited.
- **Dependencies.** Phase 4 A1 (correct contract addresses must be in place before SDK is initialized, since the SDK uses them).

### A2. Build the post-connect onboarding hooks (P0)

- **Change.** Translate the reference impl's hooks into our app. New files in `src/hooks/polymarket/`:
  - `useSafeDeployment.ts` — derives Safe address from EOA, calls relay-client to deploy.
  - `useUserApiCredentials.ts` — runs the L1 → L2 derivation (Phase 4 A3 server action wrapped in a hook).
  - `useTokenApprovals.ts` — calls relay-client batch approval for USDC.e + CTF + NegRisk + CTF Exchange.
  - `useTradingSession.ts` — top-level orchestrator that chains the above. Replaces the current `TradingOnboardingProvider` step machine.
- **Why.** Pulling these hooks out of `TradingOnboardingProvider.tsx` (which is currently 800+ lines and mixes UI state with onboarding flow) untangles the provider and lets us reuse the hooks elsewhere (e.g. settings page proxy-wallet retry).
- **Test.** A new user signs in. Each step shows the expected wallet prompt. No step is skipped.
- **Files.** New files above. `TradingOnboardingProvider.tsx` shrinks to UI state coordination only.
- **Dependencies.** A1 (SDK must be in place).

### A3. Decide and document: keep Reown for the modal? (P0 decision, P1 implementation)

- **Decision.** **Keep Reown AppKit for connector UI and wagmi context.** Rationale (per Finding 1):
  - Reown's modal already supports MetaMask, Rabby, WalletConnect, Coinbase, and over 250 other wallets; equivalent coverage from a custom modal would mean reimplementing connector orchestration.
  - Reown SIWE wiring (`@reown/appkit-siwe`) is already integrated into our `auth.ts` for session establishment; replacing it would force a parallel SIWE solution.
  - The wagmi-safe-builder-example is wagmi-config-agnostic — it consumes whatever connector store the host app provides.
- **Document.** This decision goes into `docs/adr/0002-keep-reown-appkit-for-wallet-connect.md` as an ADR (lightweight: scope, decision, consequences). Update memory file `project_clob_parity_state.md` if relevant.
- **Why.** Decisions like this need a written record so a future engineer doesn't re-litigate.
- **Files.** `docs/adr/0002-...md` (new).
- **Dependencies.** None.

### A4. (Defer post-launch) Add Magic Link as an alternate EOA source (P3)

- **Change.** Wire `@magic-sdk/...` per the `magic-safe-builder-example` and add a "Sign in with email" button in the AppKit-modal-or-Magic chooser.
- **Why.** Email auth converts users who bounce on the wallet-extension UX. Polymarket data shows email auth converts ~3x better than wallet-only.
- **When.** After A1, A2, and Phase 4 land. Not pre-launch.
- **Dependencies.** A1, A2.

### A5. (Defer post-launch) Add Turnkey as an alternate EOA source (P3)

- **Change.** Per `turnkey-safe-builder-example`. Same shape as A4.
- **When.** Same as A4 — post-launch.
- **Dependencies.** A1, A2.

## Risks

1. **A1 SDK version pinning.** The `clob-client` SDK is actively developed. Pin to a specific commit/version that we have read end-to-end at adoption time, and mirror Polymarket's lockfile if they publish one. Otherwise an SDK breaking change quietly destabilizes our prod path.

2. **A2 onboarding state explosion.** The current `TradingOnboardingProvider` already has many states (`idle | signing | deploying | completed | error`). Adding three more hooks worth of state ON TOP without consolidating could double the surface. Mitigation: build the new hooks as state machines with shared types; let `TradingOnboardingProvider` reduce its role to UI coordination only.

3. **A3 lock-in to Reown.** If Reown raises pricing or sunsets a feature we depend on, switching cost is non-trivial. Cost is bounded — we don't depend on any Reown-specific feature except the modal and SIWE — but flag for future review.

4. **Existing kuest-proxy users will need a migration.** Out of Phase 5 scope; flagged for the cutover plan (Phase 11). Migration consists of: snapshot kuest-proxy USDC balances, prompt the user to withdraw to their EOA, then re-run the onboarding flow against the new Safe.

## Status when phase is closed

Phase 5 is closed when:

- [ ] A1 merged. SDK initialized; basic order placement uses the SDK.
- [ ] A2 merged. Onboarding flow runs end-to-end on a fresh user account.
- [ ] A3 ADR written. Decision documented.

A4/A5 are not blockers for launch.
