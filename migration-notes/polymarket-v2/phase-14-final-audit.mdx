## Amber list — KNOWN UNKNOWNS with mitigation

### A1. Exact V2 Order EIP-712 signed struct (NEEDS verification at impl time)

**The wire body is documented (12 fields).** The EIP-712 signed struct is a SUBSET — `clob-openapi.yaml` says:

> "In CLOB V2, `expiration` remains in the POST /order wire body for GTD/order-expiry handling, but it is **not part of the EIP-712 signed order struct**."

So `expiration` is unsigned. The signed struct presumably is:

```
salt, maker, signer, tokenId, makerAmount, takerAmount, side,
timestamp, metadata, builder, signatureType
```

(11 fields — V1 had 12: ours dropped `taker`, `nonce`, `feeRateBps` and added `timestamp`, `metadata`, `builder`).

But this is HYPOTHESIS. The verbatim signed struct lives in `Polymarket/exchange-tools-ts` or a deeper SDK file I couldn't find via `gh`/`raw.githubusercontent`.

**Mitigation.** Phase 4 A1 implementation uses the official `@polymarket/clob-client` SDK's `createAndPostOrder` (Phase 5 A1) instead of hand-rolling the typed data. The SDK encapsulates the V2 typed data correctly. We stop maintaining `EIP712_TYPES.Order` for write paths and let the SDK do it. Our hand-rolled `signOrderPayload` becomes unused for new orders.

**Confidence with mitigation.** High. SDK is the canonical source.

### A2. Polymarket Safe deployment EIP-712 typed data

**The relayer accepts `/submit` with `type: SAFE`** and the `data` field being calldata. The signature is over a Safe-tx EIP-712 typed data. The exact struct (Safe v1.3.0 / v1.4.0 standard `SafeTx`) is widely published but the specific Safe contract addresses Polymarket uses (and any wrapper they layer on top) need verification.

Our current `src/lib/safe-proxy.ts` defines:
- Domain: `name: 'Contract Proxy Factory'`, `verifyingContract: SAFE_PROXY_FACTORY_ADDRESS`
- Type: `CreateProxy` with fields `[paymentToken, payment, paymentReceiver]`

This is **kuest's `CPMMProxyFactory`-shape**, NOT Polymarket's Safe. Polymarket uses the canonical Gnosis Safe contracts (per `magic-safe-builder-example`).

**Mitigation.** Phase 5 A1 / Phase 4 A5 implementation reads `Polymarket/wagmi-safe-builder-example/hooks/useSafeDeployment.ts` and `useTokenApprovals.ts` directly. These reference repos give us the exact EIP-712 + calldata builders. Adopt their `useSafeDeployment` pattern verbatim.

**Confidence with mitigation.** High. Reference impls are byte-accurate.

### A3. Polymarket relayer auth headers

The relayer-openapi.yaml mentions two auth modes:
- Builder API key auth: `POLY_API_KEY, POLY_TIMESTAMP, POLY_PASSPHRASE, POLY_SIGNATURE` (HMAC-SHA256)
- Relayer API key auth: `RELAYER_API_KEY, RELAYER_API_KEY_ADDRESS` (no HMAC)

Our `.env.local` already has `POLYMARKET_RELAYER_API_KEY` and `POLYMARKET_RELAYER_API_KEY_ADDRESS`. The simpler auth mode applies for our server-side relayer calls.

**Mitigation.** Phase 4 A5 uses `RELAYER_API_KEY` + `RELAYER_API_KEY_ADDRESS` headers. No HMAC for relayer.

**Confidence.** High.

### A4. Comment write auth

Polymarket comments accept reads publicly but writes require auth. The exact write-auth scheme isn't in any doc I found. We DEFER comment writes to post-launch (Phase 7 A2 + Phase 13 A4 — env-flag gated).

**Mitigation.** Read-only at launch.

**Confidence.** High that the deferral is correct.

### A5. Sports WS host

Per docs: `wss://sports-api.polymarket.com/ws` for sports events. Our sports event pages may need a separate connection from the main CLOB ws. Not yet verified live.

**Mitigation.** Phase 6 A3 will probe this at impl time.
