# Phase 0. Migration framework

Goal of this document: pin down the scope, conventions, evidence rules, and the
phase order so subsequent phase docs can reference a single source of truth and
the work stays auditable.

## Scope

Migrate the Axes frontend off the local kuest backend stack and onto Polymarket
native infrastructure, while keeping the existing frontend code surface largely
intact (kuest is a near-parity reimplementation of Polymarket, so its API
shapes already match in most places). Where the frontend talks to a kuest
service, we either repoint at the equivalent Polymarket service or build a
thin Vercel-side shim.

Out of scope for this migration: rewriting the UI, changing the database
schema beyond what the migration requires, building new chains or contracts.

## Convention: phased mdx files

Each phase doc lives at `docs/migration-polymarket/phase-NN-<topic>.mdx` and
must contain the following sections:

1. **Scope** – exactly what this phase covers, what it explicitly does not
2. **Code reading log** – every file read during the phase, with the
   `file_path:line_number` of the relevant pieces and a one-line summary
3. **Polymarket reference reading log** – every doc URL fetched, with the
   verbatim quote we relied on
4. **Findings** – numbered. Each finding has: claim, evidence, confidence
5. **Action items** – numbered. Each has: change, file targets, dependencies,
   acceptance test
6. **Risks** – what could break in production if we got step 5 wrong
7. **Status when phase is closed** – what's verified, what's deferred

Do not ship implementation in the same turn as the phase doc unless the user
explicitly asks. The phase doc is the contract; the code change comes after.
