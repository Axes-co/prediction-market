# Phase 30 - Verification of Phases 7/8/9

Independent verification of Codex's claims for Comments (Phase 22 lines 352-388), Data API/Profile/Portfolio (Phase 22 lines 390-422), Builder/Referrals (Phase 22 lines 424-458).

## Phase 7 - Comments

### Confirmations of Codex

**Holders-only client filter wipes the list.** `src/app/[locale]/(platform)/event/[slug]/_hooks/useInfiniteComments.ts:68-69` sends `holders_only=true` to `/api/comments`. Same hook at `:107-116` ALSO applies `flattened.filter(comment => hasPositivePositions(comment.positions))`. The local DB comment row schema does not store `positions` (the native comment table is event-scoped, not position-scoped). Every native comment has `comment.positions = []`, so `hasPositivePositions([])` = false, so holders-only mode renders zero comments. **Confirmed (Codex correct, Phase 22 line 368).**

**Native comments do not publish upstream.** `/api/comments POST` writes only to the local DB; no fetch to Gamma. **Confirmed.**

**`/api/sync/gamma-comments` not scheduled.** Already covered in Phase 24 (Phase 1 verification).

### New findings I add

#### F1. Live RTDS comments filter mismatch (carryover from Phase 29)

`useLiveCommentsChannel.ts:131` filter is `{ event_slug }`, but Polymarket RTDS payload carries `parentEntityID` + `parentEntityType` (per `/tmp/polymarket-llms-full.txt:4287-4302`). Native comments served from local DB ARE keyed by `event_slug`, but RTDS events from Polymarket are keyed by gamma event ID. Two different filter spaces.

**P0:** rebuild the filter to use the gamma event ID for RTDS, while still using `event_slug` for the REST query. They're separate stores.

#### F2. Comment count drift between local and Polymarket

The Gamma event payload includes `commentCount` which `gamma/mapper.ts` carries forward. Local native comments do not increment Polymarket's count. So an event seeded with 30 Gamma comments + 5 local native comments will show "30" on the count badge but render 35 in the list. This is a UX inconsistency.

**P1:** decide whether the count reflects synced + native or only synced. If the latter, separate badges.

### New findings I add

#### F3. `/v1/leaderboard` parameters need verification

`profile-link-stats.ts:184-191` builds `/leaderboard?user=...&timePeriod=all&orderBy=PNL&category=overall&limit=1&offset=0`. The Data API openapi defines `/v1/leaderboard` (line 1413), but the route uses `${leaderboardApiUrl}/leaderboard` — without the `/v1` prefix. Need to read `leaderboardApiUrl` to determine if it's a different host or same host with `/v1` baked in.

**P1:** verify exact URL shape against `data-api.polymarket.com/v1/leaderboard`.

#### F4. `setReferral` ABI / contract verification missing

`src/lib/safe/transactions.ts:106` defines `setReferral` function fragment, `:312` encodes call. Codex (Phase 22 line 442) said "verify against current CTF Exchange V2 ABI before use." I cannot verify the ABI from src/ alone — the V2 exchange contract source is in `../polymarket/ctf-exchange-v2/`. If `setReferral` isn't in the V2 ABI, this transaction reverts.

**P0 verification:** read `../polymarket/ctf-exchange-v2/contracts/CTFExchange.sol` (or equivalent) and confirm `setReferral(address referrer, address affiliate, uint256 affiliateSharePercent)` exists with the same selector. If not, this entire affiliate flow is broken on V2.

#### F5. Affiliate fee promise without backing data

`src/app/[locale]/admin/affiliate/page.tsx:101` and `src/app/[locale]/(platform)/settings/affiliate/page.tsx:40` call `fetchFeeReceiverTotals({ endpoint: 'referrers' })`. Both pages aggregate the response with `sumFeeTotals` / `sumFeeVolumes` and render numbers. With no documented `/referrers` endpoint, the page either:
1. Returns an error (4xx/5xx) — pages show stub state, or
2. Returns empty array — pages show "$0 / 0 vol".

Either way, the user sees a misleading or broken display. **Codex correct (Phase 22 line 414).**

## Phase 9 - Referrals / Partnership / Builder Fees

### Confirmations of Codex

**Builder code is signed in every order.** `src/lib/orders/index.ts:13-19,158-162` confirmed in Phase 26.

**Internal affiliate metadata is separate from builder fees.** `useAffiliateOrderMetadata` exposes `referrerAddress`, `affiliateAddress`, `affiliateSharePercent`, used by `setReferral` (`safe/transactions.ts:104-116, 308-318`). V2 order signing ignores legacy fee fields per Codex (Phase 22 line 437). **Confirmed.**

**Internal referrals are not Polymarket builder fees.** Two systems:
- Internal: signup referral cookie + DB record, used for product analytics + onchain `setReferral`.
- Builder: signed bytes32 builder code on every order, reportable via `/builder/trades` and `/v1/builders/leaderboard`.

These are not equivalent. Internal referral economics depend on the V2 contract ABI for `setReferral`; builder economics depend on Polymarket's tier mechanics.

### New findings I add

#### F6. Builder reporting infra not built

`grep` for `builder/trades` returns no consumer in `src/`. The Data API has `/v1/builders/leaderboard` and `/v1/builders/volume`, but no admin page consumes them. The CLOB has `/builder/trades?builder_code=<code>` (per `/tmp/polymarket-clob-openapi.yaml:1319-`), no consumer.

**P1:** build an admin page that pulls `/v1/builders/leaderboard` (where the code stands), `/v1/builders/volume` (cumulative volume), and `/builder/trades?builder_code=<our_code>` (per-trade breakdown). Replaces affiliate-page displays.

#### F7. `setReferral` on-chain transaction fires from onboarding

`TradingOnboardingProvider.tsx:552-559` adds `setReferral` transactions to the approval batch. If F4 is right and the ABI doesn't match, the entire approval batch reverts — every new user's onboarding fails. This is high-blast-radius.

**P0:** confirm setReferral ABI on V2 exchanges OR pull `setReferral` out of the onboarding batch and run as a separate optional step that won't bring down approvals.
