# Phase 32 - Master Launch Plan

This plan consolidates the verified blockers from Phase 23-31. Every P0 below is backed by file:line evidence I personally read and matched against the official Polymarket spec snapshots in `/tmp/polymarket-*-openapi.yaml` and the docs in `/tmp/polymarket-llms-full.txt`.

**Do not start coding until the user signs off on this plan.** The user explicitly asked for audit + plan, not implementation.

## Working agreement (per `feedback_audit_methodology.md`)

- Main thread does the work. No sub-agents for architecture or implementation.
- Live evidence required for every "shipped" claim (curl probe, tx hash, DB delta).
- Phase by phase. Don't skip ahead.
- 3-way live testing where possible (axes vs kuest vs polymarket production).
- Senior code only. No patches over root causes.

## Execution priority order

The 12 verified P0 blockers below are ordered by **blast radius if violated** (highest first), not by build difficulty. A user can lose money or be exposed to compliance risk if any of P0-1 through P0-6 are violated; the rest are "broken UX, not lost funds."

### P0-4. Relayer `/submit` response handling (blast = orphaned tx state)

`/submit` returns `transactionID` + `STATE_NEW`, not `txHash`. Three call sites read `txHash` directly and either store `null` or wrong-undefined. Approvals are marked `completed` immediately on `/submit` 200 — before they're broadcast.

**Files to edit:**
- `src/app/[locale]/(platform)/_actions/proxy-wallet.ts:211` — return `{ transactionID, state }` instead of `txHash`. Update caller (`proxy-wallet.ts:74-85`) to handle pending state.
- `src/app/[locale]/(platform)/_actions/approve-tokens.ts:140-153` — gate `markTokenApprovalsCompleted` on confirmation, not on `/submit` 200.
- `src/app/[locale]/(platform)/portfolio/_actions/pending-deposit.ts:221-231` — return `{ transactionID, state }`.
- New file: `src/lib/polymarket/relayer-poll.ts` exporting `pollRelayerTransaction(transactionID, { timeoutMs })` that polls `GET /transaction?id=<id>` until `STATE_CONFIRMED`/`STATE_FAILED`/timeout.
- Schema migration: add `proxy_wallet_relayer_transaction_id`, `proxy_wallet_state` columns. Or reuse existing columns if naming permits.

**Evidence:** Phase 27.

**Acceptance:**
- `POST /api/proxy-wallet/deploy` returns 200 with `{ transactionID, state: "STATE_NEW" }`.
- Background worker (or client polling) updates status to "deployed" once `getCode(proxyAddress)` returns non-empty AND relayer state = STATE_CONFIRMED.
- Approvals do not flip to "completed" in DB until both relayer state confirmed AND on-chain `getApproval` reads non-zero.

### P0-6. `setReferral` ABI verification (blast = onboarding reverts)

`TradingOnboardingProvider.tsx:552-559` adds `setReferral` transactions to the new-user approval batch. If the V2 exchange's `setReferral(address, address, uint256)` signature doesn't match, every new-user onboarding reverts (the batch is atomic).

**Files to verify (read, then decide):**
- `../polymarket/ctf-exchange-v2/contracts/CTFExchange.sol` (or equivalent) — confirm `setReferral` selector and parameter shape.
- `src/lib/safe/transactions.ts:104-116` — local ABI fragment.
- `src/lib/safe/transactions.ts:308-318` — `buildSetReferralTransactions` call site.

**Decision tree:**
- If ABI matches: keep in batch; verify with one tiny live tx.
- If ABI mismatch or function doesn't exist on V2: pull `setReferral` out of `TradingOnboardingProvider:552-559` batch entirely. Run as a separate opt-in transaction post-onboarding so it cannot revert the approval batch.

**Evidence:** Phase 30.

## Live verification gates (gate launch on these)

1. `curl https://gamma-api.polymarket.com/events/keyset?limit=5` returns 200 + events array.
2. `curl https://clob.polymarket.com/midpoint?token_id=<token>` returns `{ "mid_price": "0.50" }`.
3. `curl -H "POLY_API_KEY: ..." -H "POLY_ADDRESS: ..." -H "POLY_SIGNATURE: ..." -H "POLY_PASSPHRASE: ..." -H "POLY_TIMESTAMP: ..." https://clob.polymarket.com/data/orders` returns user's open orders.
4. `curl -X POST -H "POLY_BUILDER_*: ..." -d '<safe-tx>' https://relayer-v2.polymarket.com/submit` returns `{ transactionID, state: "STATE_NEW" }`.
5. `curl https://relayer-v2.polymarket.com/transaction?id=<transactionID>` returns array with `transactionHash` once broadcast.
6. WebSocket connect to `wss://ws-subscriptions-clob.polymarket.com/ws/market` + subscribe + send PING every 10s + stay alive 30 minutes.
7. WebSocket connect to `wss://ws-live-data.polymarket.com` + subscribe to `comments` with `parentEntityID` filter + send PING every 5s + receive `comment_created` events.
8. Tiny pUSD split + merge round-trip on Polygon (any small market): user ends with same pUSD balance, sees yes/no token transitions in the middle.
9. Tiny limit-order BUY against an active Polymarket market via the app's order panel: order appears on `/data/orders` with correct `order_type`. Cancel: order removed.
10. Builder-attributed trade verification: after a tiny order matches, `curl /builder/trades?builder_code=0x23a45b95...` shows the trade.

If any of 1-10 fails, do not launch.

## Final readiness opinion

The migration base is sound. The CLOB order body, EIP-712 V2 domain, builder code attribution, Gamma sync direction, and pricing endpoint inventory are all correct. The launch is blocked by:

1. Infra gates (env, crons, geoblock).
2. Wire-shape bugs (relayer response, neg-risk domain, `/data/orders` field).
3. Asset-moving correctness (pUSD vs USDC.e, V2 vs UMA adapters).
4. Live-data plumbing (heartbeats, RTDS filter shape).
5. Stale Axes endpoints (USER_PNL, COMMUNITY, /volume, /referrers, CREATE_MARKET).

None of these are speculative. Every one has a file:line citation in this plan and a Polymarket spec citation backing it. The remaining work is tactical fixes plus tiny-value live verification, not refactoring.

**Estimated implementation time** assuming senior-level execution and no context drift: 2-3 working days for all P0s + 1 day for the live-probe verification gates. Faster than that risks shipping a regression.

**Ready to proceed when:** the user reviews this plan, picks a P0 sequence (suggested: P0-7 → P0-1 → P0-5 → P0-8 → P0-3 → P0-4 → P0-2 → P0-6 → P0-9 → P0-10 → P0-11 → P0-12, ordered by build-on-build dependency), and confirms whether to start coding or to do further audit on anything I covered above.
