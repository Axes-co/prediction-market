# Phase 4. Trading core

## Scope

The full money path from a user clicking "Buy" to an order being matched on
Polymarket. Specifically:

1. The EIP-712 typed data the wallet signs for the order itself
2. The auth headers and HMAC signature on every CLOB write request
3. The L1 → L2 derivation flow that mints the user's CLOB API key once per
   account
4. Builder attribution (POLY_BUILDER_CODE) on every routed order
5. Cancel-order, cancel-all-orders, cancel-market-orders parity with
   Polymarket
6. Token approvals against the relayer (currently `${RELAYER_URL}/...`)
7. Proxy wallet creation flow against the relayer

Out of scope here: wallet/auth UX choice (Reown vs Magic+Safe proxy) — Phase
5; websocket order/trade event subscription — Phase 6; geoblock — Phase 9;
builder dashboard / fees UI — Phase 10.

### Polymarket CTF Exchange contract addresses

The Polymarket Polygon mainnet CTF Exchange and NegRisk Exchange addresses are **NOT** what we have hardcoded in `contracts.ts:11-12`. We have kuest's deployments. This is the highest-blast-radius issue in Phase 4. See Finding 1.

The canonical addresses must be sourced from one of:

- The Polymarket TypeScript clob-client (Polygon constants module — `src/utilities.ts` partial; full address constants live in a config file not included in the snippet I retrieved).
- Polymarket's published docs (`docs.polymarket.com/concepts/onchain-contracts` or similar).
- On-chain verification: query the live `clob.polymarket.com/auth/contracts` or `clob.polymarket.com/ban-relayer-info` (TBD) and read the `verifyingContract` it tells the client to use.

**Do not flip CLOB_URL to Polymarket production until A1 is done.** Every order signed against the wrong `verifyingContract` will fail Polymarket's signature verification with `invalid order signature`.

## Findings

### Finding 1. Hardcoded CTF Exchange addresses are kuest's, not Polymarket's

**Claim.** `src/lib/contracts.ts:11-12` contains
`CTF_EXCHANGE_ADDRESS = 0xB559…61cb` and
`NEG_RISK_CTF_EXCHANGE_ADDRESS = 0xef02…24F5`. Polymarket's mainnet CTF Exchange and NegRisk addresses are different. The EIP-712 domain in `constants.ts:33-45` uses these addresses as `verifyingContract`. So every order signed with our current build will verify against kuest's exchange contract, not Polymarket's. After cutover, every order POSTed to `clob.polymarket.com/order` will be rejected with `invalid order signature` (or `unsupported verifying contract` per the error string at `store-order.ts:111`).

**Evidence.**

- Code: `src/lib/contracts.ts:11-12`, `src/lib/constants.ts:33-45`, `src/lib/orders/signing.ts:14-37`.
- Live source: `py-clob-client/constants.py` (fetched this session) does not list the address constants directly — they live in a different module of the SDK. The exact mainnet values must be fetched from the TS clob-client's chain-id-keyed config file or a CLOB endpoint at implementation time.
- Inference: kuest deployed its own CTF Exchange clones; our addresses match the kuest deployment used for development.

**Impact.** Hard blocker. Without the right `verifyingContract`, no order placement works on Polymarket. This is the single biggest pre-launch risk.

**Confidence.** High that the addresses don't match. Medium-high on the exact correct values until verified via the TS SDK or a live `clob.polymarket.com/exchange-info` style endpoint.

### Finding 2. Auth headers are `KUEST_*` everywhere; need a literal rename to `POLY_*`

**Claim.** All CLOB write paths and all relayer calls in our code send headers with the `KUEST_` prefix. Polymarket requires `POLY_` (live-verified verbatim from `py-clob-client/headers/headers.py`).

**Evidence.**

The grep over `src/` found `KUEST_*` headers at:

- `_actions/store-order.ts:317-322` (POST `/order`)
- `_actions/cancel-order.ts` (DELETE `/order`)
- `_actions/cancel-market-orders.ts`
- `portfolio/_actions/cancel-all-orders.ts`
- `_actions/trading-auth.ts:95-98` (L1 derivation `KUEST_ADDRESS/SIGNATURE/TIMESTAMP/NONCE`)
- `_actions/approve-tokens.ts:58-62, 133-137` (relayer calls)
- `_actions/proxy-wallet.ts:174-178` (relayer calls)
- `portfolio/_actions/pending-deposit.ts:81-85, 158-...` (relayer calls)
- `api/open-orders/route.ts` and `api/events/[slug]/open-orders/route.ts`

**Impact.** Hard blocker. Polymarket will reject every authenticated request with 401.

**Confidence.** High.

### Finding 3. HMAC algorithm and EIP-712 Order type are byte-for-byte identical to Polymarket

**Claim.** Our `buildClobHmacSignature` and our `EIP712_TYPES.Order` struct match Polymarket's contract exactly. No code changes needed for these once Findings 1+2 are resolved.

**Evidence.**

- HMAC: `src/lib/hmac.ts:8-20` performs the same operation as `py_clob_client.signing.hmac.build_hmac_signature` — base64-decode the secret, HMAC-SHA256 over `timestamp+method+normalizedPath+body`, base64-encode, URL-safe replace.
- EIP-712 Order: `src/lib/constants.ts:47-62` lists 12 fields with the same names and types as Polymarket's signed-order struct: `salt, maker, signer, taker, tokenId, makerAmount, takerAmount, expiration, nonce, feeRateBps, side, signatureType`.
- Domain `name='CTF Exchange'`, `version='1'`: matches Polymarket's domain (only `verifyingContract` and `chainId` differ — `chainId` matches because both run Polygon mainnet).

**Impact.** Net positive — these are already done. Means Phase 4's surface area is smaller than it would be on a green-field port.

**Confidence.** High.

### Finding 4. Builder code is supported in Polymarket's clob-client but not yet wired into our order payload

**Claim.** Polymarket builders attach `POLY_BUILDER_CODE` to every routed order. Our current `clobPayload` at `store-order.ts:282-298` does not include any builder code field; we ship orders as un-attributed.

**Evidence.**

- Polymarket docs (verbatim quote in reference reading log above): `builderCode: process.env.POLY_BUILDER_CODE!` is a parameter to `createAndPostOrder`.
- Phase 0 framework lists `POLYMARKET_BUILDER_CODE`, `POLYMARKET_BUILDER_ADDRESS`, `POLYMARKET_BUILDER_API_KEY`, `POLYMARKET_RELAYER_API_KEY`, `POLYMARKET_RELAYER_API_KEY_ADDRESS` as defined-but-unused env vars added 2026-04-28. Not yet referenced in `src/`.
- Code: `src/app/[locale]/(platform)/event/[slug]/_actions/store-order.ts:281-300` shows the JSON body sent to `/order`. There is no `builderCode` field.
- TS clob-client `NewOrder` interface (per WebFetch of `Polymarket/clob-client/blob/main/src/types.ts`) does not surface `builderCode` on the `NewOrder` interface I was able to read. The `BuilderTrade` interface exists but is read-only (response shape, not request). The exact body field is **NOT** confirmed yet.

**Open question (resolve at implementation).** Where exactly does `builderCode` go in the POST `/order` body? Three reasonable hypotheses:

1. As a top-level field next to `order`, `orderType`, `owner`: `{ order, orderType, owner, builderCode }`. This is the simplest and matches the SDK call shape.
2. As an additional field inside the signed order's EIP-712 message itself (`builderCode` becomes part of the signed payload). This would require updating the EIP-712 `Order` struct, which the py-clob-client OrderArgs does NOT show.
3. As a separate query string parameter on the POST URL (`POST /order?builderCode=…`).

The most likely answer based on the docs is (1). To resolve definitively: read the latest `postOrder` implementation in `Polymarket/clob-client` directly at the line referenced by `client.ts` "[remainder of file in raw view]" — fetch via `gh` or raw GitHub URL with line range — at implementation time.

**Impact.** Medium. Without builder code, our orders are not attributed to our builder profile. We forfeit fee rev share but trades still execute. Wiring this is required for the core launch goal of "we earn revenue per trade".

**Confidence.** High that builder code is required. Medium on the exact field placement until A4 implementation reads the SDK source.

### Finding 5. Trading auth's signed message is custom; Polymarket's L1 derivation has its own EIP-712 message

**Claim.** Our `TradingOnboardingProvider.tsx:398-403` signs:

```ts
{
  domain: getTradingAuthDomain(),
  types: TRADING_AUTH_TYPES,
  primaryType: TRADING_AUTH_PRIMARY_TYPE,
  message,           // includes timestamp + nonce per buildTradingAuthMessage
}
```

Polymarket's L1 derivation ("create or derive API key") uses a different EIP-712 typed data — specifically the "L1" auth scheme described in their headers module. The message signed at L1 is a fixed `string` that includes the address, timestamp, and nonce, not a custom domain/struct.

**Evidence.**

- `py-clob-client/signing/eip712.py` (need to verify in implementation) contains the L1 message constant, typically:
  - Domain: `{name: "ClobAuthDomain", version: "1", chainId: 137}`
  - Types: `{ClobAuth: [{name:"address", type:"address"},{name:"timestamp", type:"string"},{name:"nonce", type:"uint256"},{name:"message", type:"string"}]}`
  - PrimaryType: `ClobAuth`
- Our `TRADING_AUTH_TYPES` and domain are kuest-defined (need to read `src/lib/trading-auth/{client,server,utils}.ts` to confirm).

**Impact.** L1 derivation is a one-time event per user. If our typed data is structurally different from Polymarket's, the L1 sig will fail signature recovery and Polymarket will refuse to mint an API key.

**Confidence.** Medium-high. The general shape of L1 in py-clob-client is well known; our specific struct needs a side-by-side comparison.

### Finding 6. Relayer paths and proxy-wallet flow are kuest-shaped; Polymarket relayer is different

**Claim.** Our `proxy-wallet.ts`, `approve-tokens.ts`, and `pending-deposit.ts` make POST requests to `${RELAYER_URL}/...` paths defined by the kuest relayer service. Polymarket's relayer (`relayer-v2.polymarket.com` per Phase 0 framework) uses a different endpoint structure — defined by the OpenAPI spec at `docs.polymarket.com/api-spec/relayer-openapi.yaml`.

**Evidence.**

- Code at `_actions/proxy-wallet.ts:147-178` and `_actions/approve-tokens.ts:54-68, 128-141`. These hit kuest-style relayer paths (likely `/safe/deploy`, `/allowances`, `/allowances/grant`).
- The Polymarket relayer flow per the builder reference repos involves Safe deployment via the `magic-safe-builder-example` and `wagmi-safe-builder-example` patterns — different signature, different endpoint shape, different acknowledgment.
- Our `src/lib/orders/signing.ts` is order-only; it does not currently sign relayer transactions. The relayer transactions (proxy deploy, token approvals) are signed inline in their respective `_actions` files.

**Impact.** Hard blocker for proxy-wallet onboarding and token-approval flow. Without these, a user can connect a wallet but cannot actually fund or trade.

**Confidence.** High that the path structure differs; the exact correct paths need to be read off the relayer-openapi.yaml.

## Risks

1. **A1 wrong-address regression.** If we transcribe the Polymarket addresses with a typo, every signed order silently fails verification. Mitigation: cross-check against a second source (TS clob-client + on-chain explorer). Keep kuest addresses behind `IS_TEST_MODE` so we can revert by env flag.

2. **A3 mismatched typed-data subtleties.** Polymarket's `ClobAuth.timestamp` is `type: 'string'` not `'uint256'` — easy to get wrong. Mitigation: copy the typed-data definition verbatim from py-clob-client's signing module, do not transcribe by hand.

3. **A4 builder code might require EIP-712 inclusion.** If it's part of the signed payload (hypothesis 2 in Finding 4), then the signature itself depends on the builder code and we cannot retrofit it without re-signing every order. Mitigation: confirm via SDK source before committing.

4. **A5 changes the user-visible signing prompt.** Today the SafeProxy signing prompt shows our custom domain; Polymarket's Safe flow shows the canonical Safe `SafeTx` typed data. Users used to the kuest UX may be confused. Mitigation: update the signing prompt copy in `TradingOnboardingProvider.tsx` to explain "you're approving Polymarket's Safe deployment".

5. **HMAC normalizedPath edge case.** Our HMAC strips `?query` from GETs (`hmac.ts:9-11`). py-clob-client's reference does the same. Verify Polymarket's relayer uses the same convention; some relayers HMAC the full URL including query. If Polymarket's relayer differs, GET `/allowances` will fail signature verification.

6. **Proxy wallet status state machine.** We have `proxy_wallet_status ∈ {none, signed, deploying, deployed}`. Polymarket's relayer may return different status enums. Mitigation: keep our enum, map their response to ours in a small adapter rather than refactoring the state machine.
