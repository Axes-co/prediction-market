# Phase 29 - Verification of Phase 6

Independent verification of Codex's Phase 6 claims (Phase 22 lines 310-351, Phase 21 lines 211-234, Phase 20 lines 602-634).

## Confirmations of Codex's findings

### No PING heartbeat anywhere

`grep -nE "PING|ping|heartbeat|setInterval.*10_?000|setInterval.*5_?000"` across the four websocket consumers (`EventMarketChannelProvider.tsx`, `useLiveCommentsChannel.ts`, `useLiveChartStream.ts`, `ActivityFeed.tsx`) returns zero matches for actual heartbeat sends. The only `setInterval` is `useLiveChartStream.ts:97-101` — a UI clock for `nowMs`, not a PING.

Per official docs:
- `https://docs.polymarket.com/market-data/websocket/overview.md` line 3786: "Send `PING` every 10 seconds. The server responds with `PONG`." (Market & User channels)
- Same doc line ~3866: "Send `PING` messages every 5 seconds to maintain the connection." (RTDS)
- Same doc line 3814: "Connection drops after about 10 seconds" → "You're not sending heartbeats."

**Verdict:** Without heartbeats, every ws client disconnects ~10s after open. The browser will reconnect, but the data stream pulses on/off every 10s, masking real disconnect events. **Codex correct.**

### No authenticated `/ws/user` implementation

`grep -rn "/ws/user\\|userChannel\\|user_channel"` in `src/` returns nothing. The four ws clients all consume:
- Market channel `${WS_CLOB_URL}/ws/market`
- RTDS `${WS_LIVE_DATA_URL}` (no path)

User channel for authenticated order/trade lifecycle is not implemented. UI gets order updates via React Query polling against `/api/open-orders` and database state.

Polymarket docs at line 3815 warn: "Do not put CLOB API key/secret/passphrase into browser websocket code. Either build a server-side user-channel bridge or keep polling `/api/open-orders`."

The current state (polling) is acceptable as a fallback, but trades feel laggy on the typical 5-10s polling interval.

**Verdict:** Codex correct that this is missing; my view is the polling fallback is launch-acceptable, with user channel as a P1 enhancement.

### `topic: 'activity', type: 'orders_matched'` is undocumented

`src/app/[locale]/(platform)/activity/_components/ActivityFeed.tsx:296-305`:

```ts
{
  action,
  subscriptions: [
    {
      topic: 'activity',
      type: 'orders_matched',
    },
  ],
}
```

RTDS docs (line 3833) explicitly say RTDS supports **comments**, **crypto prices**, and **equity prices**. Line ~3859: "Only the subscription types documented below are supported." `topic: 'activity'` is not in the documented list.

Implication: this subscription is either:
1. A legacy kuest-extension topic (kuest's RTDS may support more topics than Polymarket's),
2. A future Polymarket topic that's not yet in docs, or
3. Silently no-op'd by Polymarket's RTDS.

**Verdict:** Confirmed undocumented. Live verification against `wss://ws-live-data.polymarket.com` is needed before launch. If unsupported, replace with polling against the Data API `/activity` endpoint (which exists per `polymarket-data-openapi.yaml`).

### RTDS comments wildcard type may not match

`src/app/[locale]/(platform)/event/[slug]/_hooks/useLiveCommentsChannel.ts:124-134`:

```ts
{
  action,
  subscriptions: [
    {
      topic: 'comments',
      type: '*',
      filters: JSON.stringify({ event_slug: eventSlug }),
    },
  ],
}
```

Per official RTDS docs (line 4267-4270), the four documented `comments` types are: `comment_created`, `comment_removed`, `reaction_created`, `reaction_removed`. Wildcard `'*'` is documented for `crypto_prices_chainlink` (line 3973) but **not** for `comments` (line 4256-4260 example uses `"type": "comment_created"` explicitly).

**Verdict:** Likely doesn't work. **Live verify.** If RTDS rejects wildcard type for comments, subscribe four times (once per documented type) instead.

### `event_slug` filter may not match Polymarket's filter shape

The RTDS `comment_created` payload (line 4276-4302) carries `parentEntityID: 18396` (numeric) and `parentEntityType: 'Event'`, NOT `event_slug`. The app's `filters: JSON.stringify({ event_slug: eventSlug })` likely returns no comments because Polymarket filters by `parentEntityID`, not `event_slug`.

**P0 fix:** swap to `filters: JSON.stringify({ parentEntityID: <gamma_event_id>, parentEntityType: 'Event' })` after looking up the gamma event id from the local DB record.

## New findings I add (not in Codex)

### F1. Market channel uses `assets_ids` (correct), but no `custom_feature_enabled`

`EventMarketChannelProvider.tsx:239-249` subscribes with `type: 'market'` and `assets_ids`. Per docs (line 3675), the events `best_bid_ask`, `new_market`, and `market_resolved` require `custom_feature_enabled: true` in the subscription. The app receives `book`, `last_trade_price`, and `best_bid_ask` (per Phase 22 line 326).

If `best_bid_ask` is being received without `custom_feature_enabled: true`, that's spec drift on Polymarket's side or an undocumented allowance. Either way, set the flag explicitly to be safe.

**P1:** add `custom_feature_enabled: true` to the market channel subscription.

### F2. RTDS `gamma_auth` field unused

Per RTDS docs (line 3858): "Some user-specific streams may require `gamma_auth` with your wallet address." The Polymarket comment payload (line 4287-4292) includes `userAddress` and `proxyWallet`. For a logged-in user, including `gamma_auth: { address: <user.address> }` may unlock additional comment events (their own reactions, etc.) that anonymous subscribers don't see.

**P2:** if comments rendering misses self-events for the current user, add `gamma_auth` to the subscription.

### F3. `WS_CLOB_URL` defaults to `wss://ws-subscriptions-clob.axes.co`

`next.config.ts:111` `WS_CLOB_URL: process.env.WS_CLOB_URL ?? 'wss://ws-subscriptions-clob.axes.co'`. Without explicit Vercel env, the browser opens an `axes.co` ws connection (from Phase 23 finding). Same risk surface as the HTTP defaults — silent misroute.

Already covered in Phase 23 P0 #1.

### F4. Reconnect logic exists but does not back off after rejection

`EventMarketChannelProvider.tsx:231-359` has reconnect logic per Codex. Need to verify whether reconnect uses exponential backoff and whether it stops after N failures. If a malformed subscription gets the connection killed and the reconnect immediately re-tries with the same payload, this loops indefinitely — the user sees the page "live" indicator flapping forever.

**P1:** verify backoff strategy. Skipping deep read for now; flag as live-test target.

### F5. Sports channel not implemented

The official sports channel `wss://sports-api.polymarket.com/ws` is not consumed anywhere in `src/`. This is acceptable if sports product is pre-launch; flag if sports pages exist and rely on stale data.

`grep -rn "sports-api"` returns nothing. Sports pages currently use REST polling.

## Net Phase 6 P0 list

P0:

1. **Add PING heartbeat (every 10s) to market channel** — `EventMarketChannelProvider.tsx`. Use `ws.send('PING')` (string literal, per docs) on a setInterval, clear on close.
2. **Add PING heartbeat (every 5s) to RTDS** — `useLiveCommentsChannel.ts`, `ActivityFeed.tsx`, `useLiveChartStream.ts` if it opens a ws.
3. **Fix RTDS comments filter** — swap `event_slug` to `parentEntityID: <gamma_event_id>, parentEntityType: 'Event'`.
4. **Replace wildcard `type: '*'` with explicit comment types** — subscribe to all four documented types (`comment_created`, `comment_removed`, `reaction_created`, `reaction_removed`) until live-verified that wildcard works.
5. **Disable / feature-flag `topic: 'activity'` RTDS subscription** until live-verified, or replace with Data API `/activity` polling.

P1:

6. Add `custom_feature_enabled: true` to market channel subscription.
7. Verify reconnect backoff strategy.
8. Implement authenticated user channel (`/ws/user`) server-side bridge OR document the polling fallback explicitly.

P2:

9. Add `gamma_auth` to RTDS comments subscription for logged-in users.
10. Implement sports channel if sports product launches.
