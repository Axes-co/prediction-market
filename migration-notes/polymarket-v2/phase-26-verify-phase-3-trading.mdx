# Phase 26 - Verification of Phase 3

Independent verification of Codex's Phase 3 claims (Phase 22 lines 159-202, Phase 21 lines 135-160, Phase 20 lines 416-443). This is the highest-risk phase: signing the wrong domain or sending an undocumented field can fail every order silently or, worse, succeed against the wrong contract.

## Confirmations of Codex's findings

### V2 EIP-712 domain + 11-field Order struct

`src/lib/constants.ts:36-48` defines `EIP712_DOMAIN` and `NEG_RISK_EIP712_DOMAIN`, both with `name: 'Polymarket CTF Exchange'`, `version: '2'`, and the V2 verifying contracts from `src/lib/contracts.ts`. `:56-70` defines the 11-field Order type. `:72-74` selects between standard and neg-risk domain by `isNegRisk`. **Confirmed.**

`src/lib/orders/signing.ts:23-46` signs only the 11 V2 fields and explicitly omits `taker`, `expiration`, `nonce`, `feeRateBps` from the typed-data message. **Confirmed.**

`src/lib/orders/index.ts:145-162` builds the BlockchainOrder with: `salt`, `maker = makerAddress ?? userAddress`, `signer = userAddress`, `signature_type` (defaults 0), `timestamp = BigInt(Date.now())` ms, `metadata = ZERO_BYTES32`, `builder = resolveBuilderCode()`. **Confirmed.**

`src/lib/orders/index.ts:14-18` reads `POLYMARKET_BUILDER_CODE`, validates `^0x[a-f0-9]{64}$/i` regex, falls back to `ZERO_BYTES32`. **Confirmed.**

### Order wire body matches CLOB OpenAPI

`src/app/[locale]/(platform)/event/[slug]/_actions/store-order.ts:288-310` constructs the V2 wire body:

```ts
{
  order: { salt, maker, signer, tokenId, makerAmount, takerAmount,

           metadata, builder, signature },
  orderType: clobOrderType,

```

Matches CLOB OpenAPI `/order` POST schema. **Confirmed.**

L2 auth headers at `store-order.ts:325-333` send all five `POLY_*` headers per `polymarket-clob-openapi.yaml:514` security spec. **Confirmed.**

CLOB OpenAPI defines all three (paths at lines 28, 706, 771). **Confirmed.**

### Market-level neg-risk signing bug — CONFIRMED

`src/app/[locale]/(platform)/event/[slug]/_components/EventOrderPanelForm.tsx:842-876`:

```tsx
842   const isNegRiskEnabled = Boolean(event.enable_neg_risk)
843   const isNegRiskMarket = typeof activeMarket?.neg_risk === 'boolean'
844     ? activeMarket.neg_risk
845     : Boolean(event.enable_neg_risk || event.neg_risk)
...
876   const orderDomain = useMemo(() => getExchangeEip712Domain(isNegRiskEnabled), [isNegRiskEnabled])
```

Bug: line 876 uses `isNegRiskEnabled` (event-level only). The market-aware value `isNegRiskMarket` is computed but only used for non-signing purposes (UI/onboarding). For multi-market events where one child market has `neg_risk = true` and the parent event has `enable_neg_risk = false` (or vice versa), the order signs against the **wrong** exchange domain. Submission still succeeds locally but fails verification on-chain. **Confirmed (Codex's most important finding).**

### Profile cash-out neg-risk over-classification

`src/app/[locale]/(platform)/profile/_components/PublicPositionsList.tsx:694`:

```ts
isNegRisk = Boolean(payload?.data?.event_enable_neg_risk || payload?.data?.neg_risk)
```

Then at `:864` `getExchangeEip712Domain(isNegRisk)`. If event-level is `true` but the specific market is `false`, this signs against the neg-risk domain incorrectly. Codex flagged this as "over-classify"; concur. The fix is `isNegRisk = typeof payload?.data?.neg_risk === 'boolean' ? payload.data.neg_risk : Boolean(payload?.data?.event_enable_neg_risk)` — prefer market-level when available.

### `/data/orders` undocumented `maker` query parameter

`src/app/api/open-orders/route.ts:117-118`:

```ts
if (makerAddress) {
  params.set('maker', makerAddress)
}
```

CLOB OpenAPI `/tmp/polymarket-clob-openapi.yaml:514-555` documents `id`, `market`, `asset_id`, `next_cursor` only — no `maker`. Polymarket may accept the param and silently ignore it (in which case the route returns *all* orders authenticated to the API key, then the caller filters), or it may 400. **Confirmed undocumented (Codex correct).**

### `/data/orders` response field `order_type`, code reads `type`

CLOB OpenAPI examples at `/tmp/polymarket-clob-openapi.yaml:585,600,671` use `order_type: GTC` in the response. Code at `src/app/api/open-orders/route.ts:35` types `type?: ClobOrderType` and `src/lib/clob-open-orders.ts:16-17` types `type?: string | null`. `clob-open-orders.ts:59` reads `normalizeClobOrderType(order.type)` which silently defaults to `'GTC'` for any missing/unknown value (line 32). The user always sees "GTC" regardless of the real order type. **Confirmed (Codex correct).**

## New findings I add (not in Codex)

### F1. Builder field defaults to `ZERO_BYTES32` silently

`src/lib/orders/index.ts:18` `return ZERO_BYTES32` when `POLYMARKET_BUILDER_CODE` is unset or malformed. `.env.example` does not document `POLYMARKET_BUILDER_CODE`. If the operator misses the env var, every order signs and submits with builder=zero, getting **zero** builder attribution. The order succeeds; the partnership economics fail silently.

**P1:** at startup, log a warning when `POLYMARKET_BUILDER_CODE` is unset in production. Or fail-fast in `resolveBuilderCode()` when `process.env.NODE_ENV === 'production'`.

### F2. Cancel response shape unknown

`cancel-order.ts:65-91` reads `payload.error || payload.message` for failures, but does not parse the success response. Per official Polymarket docs the cancel response should include `canceled` / `not_canceled` arrays. The store-order success at `:91` returns `{ error: null }` without surfacing partial cancels (e.g., race condition where the order partially filled between request build and CLOB receipt).

**P1:** parse `canceled` / `not_canceled` from the response body and surface to UI when `not_canceled` is non-empty.

### F3. Order salt may not meet CLOB uniqueness requirement

`src/lib/orders/index.ts:59-78` (`generateOrderSalt`) builds a 64-bit value from two `Uint32` reads. If both `Uint32` reads happen to be zero (vanishingly rare), the fallback uses `Math.random() * MAX_SAFE_INTEGER` — fine, but the conversion via `BigInt(fallback || Date.now())` means salt could collide with `Date.now()` ms-precision in degenerate cases. Polymarket's CLOB rejects orders with the same `salt` for the same `signer` to prevent replay.

**P2 hardening:** generate a 256-bit salt directly from `crypto.getRandomValues(new Uint8Array(32))` per the V2 spec, instead of 64 bits. Risk is theoretical; not a launch blocker.

### F4. `feeRateBps` is still on the wire in non-V2 paths

`src/lib/orders/index.ts:165-179` (`serializeOrder`) emits `nonce` and `fee_rate_bps` to the wire body. `store-order.ts:292-310` correctly excludes them from `clobPayload.order`, but they sit in the action input shape, which means callers can pass them and assume they affect the order. They don't.

**P2 cleanup:** drop V1-only fields from the action input zod schema and the `BlockchainOrder` type. Currently kept "for back-compat" per comment at `index.ts:51-53`; cutoff is V2.2.

### F5. `expiration` semantics unclear when `clobOrderType` is GTC

CLOB OpenAPI documents `expiration` as wire-only; if non-zero, treated as GTD. Code at `index.ts:141-143` accepts `expirationTimestamp`; at store-order.ts:300 emits it always. If the caller passes `clobOrderType: 'GTC'` with a non-zero `expirationTimestamp`, behavior depends on the CLOB's own resolver (some implementations downgrade to GTD; others reject).

**P1:** either zero-out `expiration` when `clobOrderType !== 'GTD'`, or document the assumption.

### F6. Open-orders flow doesn't surface `next_cursor` to UI

`route.ts:91` returns `{ data, next_cursor }` from CLOB but the consumers (`useUserOpenOrdersQuery` / `useEventOrderPanelOpenOrders`) likely show only the first page. CLOB pagination via `next_cursor` is only useful if the UI requests page 2.

Worth verifying before launch but not strictly a blocker if the typical user has fewer than the page size of open orders.

## Net Phase 3 P0 list

P0:

1. **Fix neg-risk domain selection in event order form** — change `EventOrderPanelForm.tsx:876` to `getExchangeEip712Domain(isNegRiskMarket)` (already computed at line 843-845). Add a unit test that signs against the correct domain when market-level and event-level neg-risk disagree.

2. **Fix neg-risk derivation in profile cash-out** — change `PublicPositionsList.tsx:694` to prefer market-level `neg_risk` when present:
   ```ts
   isNegRisk = typeof payload?.data?.neg_risk === 'boolean'
     ? payload.data.neg_risk
     : Boolean(payload?.data?.event_enable_neg_risk)
   ```

3. **Fix `/data/orders` query** — remove the `maker` query param at `open-orders/route.ts:117-118`. Either rely on CLOB's authenticated-user filter (the `POLY_API_KEY` is the implicit identity), or filter locally after fetch if Polymarket returns orders for *all* of that API key's assets. Verify behavior against `clob.polymarket.com/data/orders` live before deciding.

4. **Fix open-orders response normalization** — change `clob-open-orders.ts:16-17` to `order_type?: string | null` and read `order.order_type` (with `order.type` as legacy fallback). `route.ts:35` `interface ClobOpenOrder` should likewise use `order_type`.

P1:

5. Fail-fast or warn when `POLYMARKET_BUILDER_CODE` is unset at startup (F1).
6. Surface cancel partial-success arrays to UI (F2).
7. Zero-out `expiration` when `clobOrderType !== 'GTD'` (F5).

P2:

8. Drop V1 fields (`nonce`, `fee_rate_bps`, `taker`) from `BlockchainOrder` type post V2.2 (F4).
9. Use 256-bit salt (F3).
