# Phase 22 - Full API Reference App Cross-Audit

This audit refreshes the source of truth from the current Polymarket API reference and cross-references it against the Axes Next.js app phase by phase. It is written as the implementation brief for Claude or any coding agent that works next.

## Senior Assessment

The app is architecturally close to Polymarket because Kuest/Axes copied the same product model: Gamma-like market discovery, CLOB-like trading, proxy wallets, local orderbook UI, portfolio views, comments, admin settings, and sports pages. That is why the migration is feasible.

The current code is not clean enough to launch full Polymarket production trading this week without fixing blockers. The trading order body is mostly right, but several surrounding flows can break real users or create compliance risk:

- Geoblock is not enforced even though Polymarket docs explicitly warn builders to implement checks before trading.
- The relayer response handling expects `txHash`, while current relayer docs say `/submit` returns `transactionID` and `STATE_NEW`; tx hash comes from `GET /transaction`.
- pUSD and current adapter usage is inconsistent in CTF split/merge/redeem/convert flows.
- Market-level neg-risk domain selection is wrong in the event order form.
- Websocket heartbeats and server-safe user-channel handling are missing.
- Old Axes-only endpoints still power profile, admin, affiliate, create-market, and geoblock flows.
- Prior docs contain stale conclusions and sensitive material. Do not publish them.

## Phase 0 - Legal, Security, Environment, Cutover Baseline

Official evidence:

- API introduction says Gamma/Data are public, CLOB trading endpoints require auth, and Bridge API is separate: `https://docs.polymarket.com/api-reference/introduction.md`.
- Authentication docs say CLOB trading endpoints require all five `POLY_*` L2 headers: `https://docs.polymarket.com/api-reference/authentication.md`.
- Geoblock docs warn that orders from blocked regions will be rejected and builders should implement geoblock checks before users attempt to trade: `https://docs.polymarket.com/api-reference/geoblock.md`.
- Current geoblock docs list `US` as blocked. That means a US user must not be allowed to place Polymarket orders through Axes.

App evidence:

- `next.config.ts:101-112` defaults all production integration URLs to Axes hosts.
- `src/proxy.ts:95-108` exempts `/geoblock`, rate-limits `/api/*`, then returns for APIs without geoblock enforcement.
- `src/proxy.ts:141-163` only handles auth/admin protection, not country blocking.
- `src/app/[locale]/admin/(general)/_actions/update-general-settings.ts:146-165` still syncs to `GEOBLOCK_URL`.
- Phase 16 and Phase 19 notes contain stale conclusions and sensitive env/credential material.

Verdict:

- Blocked. This is the highest compliance and production-safety phase.

Claude tasks:

- Replace Axes URL defaults with no fallback or explicit Polymarket production defaults in server-only runtime config. Avoid exposing secrets through `next.config.ts env`.
- Add Vercel country/region geoblock enforcement in `src/proxy.ts` before page access and before trading/API mutations.
- Ensure `/api/comments` read-only/listing can remain available if product wants comments in blocked regions, but trading, order, relay, funding, and CTF mutation routes must be blocked.
- Remove or disable external `GEOBLOCK_URL` sync.
- Redact stale migration docs and rotate any leaked builder/relayer credentials.

Acceptance:

- Requests from blocked `x-vercel-ip-country` values redirect pages to `/geoblock`.
- Trading APIs return a blocked response before touching CLOB/relayer.
- No browser JS contains builder credentials, CLOB secrets, relayer secrets, or server-only auth material.

## Phase 3 - CLOB Auth, Orders, Cancels, Open Orders

Official evidence:

- Authentication docs require CLOB trading/cancel/heartbeat endpoints to use all five L2 headers: `POLY_ADDRESS`, `POLY_API_KEY`, `POLY_PASSPHRASE`, `POLY_TIMESTAMP`, `POLY_SIGNATURE`.
- CLOB OpenAPI `Order` schema requires `maker`, `signer`, `tokenId`, `makerAmount`, `takerAmount`, `side`, `expiration`, `timestamp`, `builder`, `signature`, `salt`, and `signatureType`; it states `expiration` is wire-only and not part of the V2 signed struct.
- CLOB OpenAPI `SendOrder` requires top-level `order` and `owner`; `orderType` and `deferExec` are optional.
- CLOB OpenAPI `/data/orders` supports `id`, `market`, `asset_id`, and `next_cursor`; it does not list a `maker` query parameter.
- CLOB OpenAPI open-order examples use `order_type`, not `type`.
- CLOB OpenAPI has `DELETE /order`, `DELETE /cancel-all`, and `DELETE /cancel-market-orders`.

App evidence:

- `src/lib/constants.ts:33-74` defines V2 EIP-712 domains and the 11-field Order struct.
- `src/lib/orders/signing.ts:23-45` signs exactly those 11 fields.
- `src/lib/orders/index.ts:123-162` sets maker, signer, `signature_type`, timestamp, metadata, and builder code.
- `src/app/[locale]/(platform)/event/[slug]/_actions/store-order.ts:288-310` builds the V2 `/order` body.
- `src/app/[locale]/(platform)/event/[slug]/_actions/store-order.ts:324-335` sends CLOB L2 headers.
- `src/app/[locale]/(platform)/event/[slug]/_components/EventOrderPanelForm.tsx:842-876` computes market-level neg-risk but signs using event-level neg-risk.
- `src/app/api/open-orders/route.ts:116-132` sends undocumented `maker` to `/data/orders`.
- `src/lib/clob-open-orders.ts:56-66` maps `type`, but the OpenAPI examples use `order_type`.
- `src/app/[locale]/(platform)/event/[slug]/_actions/cancel-order.ts:34-61` uses `DELETE /order` with `orderID`.
- `src/app/[locale]/(platform)/event/[slug]/_actions/cancel-market-orders.ts:63-93` uses `DELETE /cancel-market-orders` with `market` and `asset_id`.

Verdict:

- Order submit/cancel core is mostly correct.
- Launch blockers remain: market-level neg-risk signing, open-order query/field mismatch, and live verification.

Claude tasks:

- Change `EventOrderPanelForm.tsx` to pass `isNegRiskMarket` into `getExchangeEip712Domain`.
- Change profile/cash-out signing to prefer market-level `neg_risk`; do not OR event-level flags unless market value is absent.
- Remove `maker` from `/data/orders` query or confirm live that CLOB accepts it; filter locally if needed.
- Normalize `order_type` in `mapClobOpenOrder` in addition to `type`.
- Consider sending explicit `deferExec: false` on `/order` to match docs examples.
- Add live probes for order submit, cancel single, cancel market, cancel all, open orders, and builder-attributed trade lookup.

Acceptance:

- Normal and neg-risk buy/sell orders sign with the correct verifying contract.
- `/data/orders` renders correct type, status, expiration, size, and market metadata.
- Cancel routes return and display documented `canceled`/`not_canceled` results.

## Phase 4 - Proxy Wallet, Relayer, Safe Execution

Official evidence:

- Builder overview says relayer access covers gas-free wallet deployment, approvals, order execution, and CTF operations.
- Builder tiers say unverified builders have 100 relayer transactions/day and verified builders have 10,000/day.
- Relayer OpenAPI `/submit` is authenticated with Builder API Key headers or Relayer API Key headers.
- Relayer OpenAPI `/submit` returns immediately with `transactionID` and `state: STATE_NEW`; it explicitly says onchain `transactionHash` is not included and must be retrieved by polling `GET /transaction`.
- Relayer OpenAPI `/nonce` takes the user's signer address and `type=PROXY|SAFE`.

App evidence:

- `src/lib/polymarket/relayer-auth.ts:34-57` builds `POLY_BUILDER_*` headers server-side.
- `src/app/[locale]/(platform)/_actions/proxy-wallet.ts:145-176` submits `SAFE-CREATE` to `/submit`.
- `src/app/[locale]/(platform)/_actions/proxy-wallet.ts:211` returns only `responsePayload.txHash`.
- `src/app/[locale]/(platform)/_actions/approve-tokens.ts:28-57` reads `/nonce?address=<user.address>&type=SAFE`.
- `src/app/[locale]/(platform)/_actions/approve-tokens.ts:109-155` submits Safe transactions and only extracts tx hash variants.
- `src/app/[locale]/(platform)/portfolio/_actions/pending-deposit.ts:195-231` submits wrap transactions and only extracts tx hash variants.

Verdict:

- Relayer auth direction is correct, but response handling is wrong against the current OpenAPI.

Claude tasks:

- Update relayer submit actions to store `transactionID` and `state`, not only `txHash`.
- Add a server action/helper to poll `GET /transaction?id=<transactionID>` and resolve `transactionHash`/state.
- Update proxy wallet deployment status to handle `STATE_NEW`, pending, confirmed, failed, and deployed-bytecode checks.
- Update approval and pending-deposit flows to show "submitted/pending" if only `transactionID` exists.
- Confirm HMAC timestamp units live against relayer SDK/current API. Keep builder secrets server-only.

Acceptance:

- Proxy deployment, approval batch, and pending wrap all show a stable pending state immediately after `/submit`.
- A later poll updates tx hash and deployed/confirmed state.
- No flow assumes `/submit` returns tx hash.

## Final Readiness Opinion

The app is a strong migration base and the UI/product shape fits Polymarket well. The code is not yet "legal, clean, perfect, and works" because production compliance gates and money-moving flows are incomplete. The highest-risk issues are geoblock, relayer response semantics, pUSD/CTF defaults, neg-risk signing domain, websocket/user lifecycle, and stale Axes endpoints.

The next work should not be broad refactoring. It should be a targeted blocker-close sequence using the phases above, with live probes after each phase.
