## Phase 10 - Admin / Create-Market

### Confirmations of Codex

**Admin geoblock still POSTs to `GEOBLOCK_URL`.** Already confirmed in Phase 23 (`update-general-settings.ts:146-165`).

### New findings I add

#### F1. The 7,242-line component is itself a launch risk

`AdminCreateEventForm.tsx` is a single 7K-line client component with form state, signing flows, multi-step workflow management (`prepare-auth → prepare → finalize → tx-confirm`), and onchain market deployment. Even if `CREATE_MARKET_URL` were rewired to a working backend, the component is fragile and tightly coupled to its current backend's response shapes.

Decision tree:
1. **Disable admin create-market for launch.** Hide the route, keep the file (rollback safety). Admins can manage display/visibility of synced Polymarket events.
2. **Keep create-market alive on a parallel backend.** Continue running the kuest-style create-market service (it's a separate Rust service) and deploy markets from there into Polymarket's CTF Exchange V2. Requires Polymarket's contract to accept third-party market creation, which it may not (need to verify against `../polymarket/ctf-exchange-v2`).

For week-one launch, option (1) is the only safe choice.

#### F2. `/api/sync/event-creations` runs unscheduled

Per Phase 24 finding F2, this route exists but is not in `vercel.json` cron. It can still be triggered manually from admin or via direct HTTP. If admin create-market is hidden, this route should also be disabled or made admin-only.

#### F3. Allowed-creator wallet model still active

`/api/sync/events` (legacy) and `/api/sync/gamma` both consult `loadAllowedMarketCreatorWallets` / `AllowedMarketCreatorRepository.listGammaApiSources`. This is the kuest model where market creators are wallets recognized by the platform. On Polymarket cutover, Polymarket itself is the only "creator" — but the data model treats Polymarket's Gamma API as a `gamma_api` source row.

**P1:** confirm that the allowed-creator UI in admin only shows Gamma API sources after cutover, not legacy "wallet" sources.

**US is in `ALLOWED_COUNTRY_CODES`.** `geoblock-settings.ts:244 'US'`. This is the *parser* allow-list (a country must be a valid ISO code to be parsed, not "allowed in product"). Whether US is blocked is up to admin's `blocked_countries` setting.

### New findings I add

#### F4. `ALLOWED_COUNTRY_CODES` is mis-named

The constant `ALLOWED_COUNTRY_CODES` at `geoblock-settings.ts:8` is a parser whitelist for ISO-3166 codes — it is NOT a list of countries allowed to use the product. The actual blocking is config-driven via `blocked_countries`. The naming creates confusion (a future reader sees "ALLOWED_COUNTRY_CODES" and assumes a positive allow-list, not a parser sanity check).

**P2 cleanup:** rename to `KNOWN_ISO_3166_COUNTRY_CODES` or `RECOGNIZED_COUNTRY_CODES`. Not a launch blocker.

#### F5. Geoblock endpoint and trading endpoint both need enforcement

Polymarket geoblock docs (`https://docs.polymarket.com/api-reference/geoblock.md`) say orders from blocked regions get rejected by the CLOB. The frontend doesn't need to *prevent* the request — Polymarket will reject it. But the docs also say "builders should implement geoblock checks before users attempt to trade" so users don't see confusing errors.

So enforcement strategy must be:
1. **Page-level redirect** to `/geoblock` for blocked countries (UI ergonomics).
2. **API-mutation block** for trading actions, returning a 403 before reaching CLOB (defense-in-depth + clearer error message).

The current code does neither. Both need adding.

#### F6. Default block list not seeded

There is no migration / startup seeding of `blocked_countries`. A fresh deploy has the setting empty. Users from any country (including US, which Polymarket explicitly blocks) reach the trading flow.

**P0:** seed `blocked_countries` at migration time with at least the Polymarket-blocked set. Per Polymarket docs the current blocked list includes US (and several others). Need to extract the canonical list from `https://docs.polymarket.com/api-reference/geoblock.md` and pre-seed it in `src/lib/db/migrations/`.

#### F7. Geoblock check happens AFTER `/api/*` rate limit

`src/proxy.ts:102-108` runs rate-limit, then returns `NextResponse.next()` for any `/api/*` route. To enforce country blocking on API routes, the country check needs to happen in this branch BEFORE returning. Current ordering in middleware doesn't matter for the `/api/*` case because there's no enforcement at all; this is a structural note for the fix.

**P0 implementation note:** add country check inside the `/api/*` block, scoped to mutation routes (POST/DELETE/PATCH) AND specifically to trading-adjacent routes (`/api/store-order`, `/api/cancel-*`, `/api/relayer/*`, `/api/approve-tokens`, `/api/proxy-wallet`, `/api/comments` POST). Allow GET reads to bypass for users to see synced data even from blocked regions (or apply per-product policy).

### Phase 11 (geoblock)

P0:

1. **Enforce country blocking in `src/proxy.ts`** for both pages and API mutation routes. Code shape:
   ```ts
   const country = getRequestCountryCode(request.headers)
   const blocked = isCountryBlocked(country, await loadBlockedCountries())
   if (blocked && url.pathname.startsWith('/api/')) {
     // For mutation routes, return 403 JSON
     if (request.method !== 'GET') {
       return NextResponse.json({ error: 'restricted_region' }, { status: 403 })
     }
   } else if (blocked) {
     // For page routes, redirect to /geoblock
     return NextResponse.redirect(new URL('/geoblock', request.url))
   }
   ```
   Add this *before* the existing `/api/*` rate-limit branch.

2. **Seed `blocked_countries` at migration time** with Polymarket's canonical blocked set (US + sanctioned jurisdictions). Pull from `https://docs.polymarket.com/api-reference/geoblock.md`.

3. **Remove or disable `syncGeoblockSettings` external POST** (already noted).

4. **Add `loadBlockedCountries` to a fast path / cached read** — middleware runs on every request, hitting the DB on every request kills performance. Cache for 60s in middleware.

P2:

5. Rename `ALLOWED_COUNTRY_CODES` to `RECOGNIZED_COUNTRY_CODES` to avoid confusion (F4).
